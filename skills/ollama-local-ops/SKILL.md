# 本地模型（Ollama）性能实测 + 零安装网页界面

## 0. 先分清两件事（用户经常混着问）

| 用户想要 | 实际是什么 | 怎么给 |
|---|---|---|
| 「有操作界面吗」 | Ollama 是**纯 CLI 服务**，CLI 版不带界面 | 见 §3（零安装网页台） |
| 「测一下性能」 | 与界面**无关**，直接打 API 拿自报指标 | 见 §1 |

先问清是哪一件，别一头扎进装 Open WebUI（≥1GB，多数场景过剩）。

## 1. 怎么测才算数：用 API 自报指标，别用秒表

Ollama 的 `/api/generate`、`/api/chat` 在 **final chunk** 里直接给全部分解耗时（单位 ns）：

| 字段 | 含义 |
|---|---|
| `load_duration` | 模型加载到 GPU 的耗时（**冷启动**） |
| `prompt_eval_count` / `prompt_eval_duration` | 预填充 token 数 / 耗时 → **预填充 t/s** |
| `eval_count` / `eval_duration` | 生成 token 数 / 耗时 → **解码 t/s**（唯一硬指标） |
| `total_duration` | 服务端总耗时 |

**要点**
- **一定要 `stream: true`** 才能拿到 TTFT（首字延迟）：自己记「发出请求 → 第一个非空 chunk」的墙钟。
- **冷启动要单独测**：先 `POST /api/generate {"model":M,"keep_alive":0}` 卸载，确认 `ollama ps` 为空，再发一次请求，读 `load_duration`。否则模型是热的，`load_duration≈0.01s`，数据会骗人。
- **内存占用**看 `ollama ps` 的 `SIZE` / `PROCESSOR` 列（比 `ps aux` 的 RSS 准）。`UNTIL` 列能看到多久后自动卸载。
- 报告里**预填充和解码必须分开列**：预填充可到 1332 t/s，解码只有 15 t/s，混在一起讲会得出完全错误的结论。

## 1.5 判断「这台机器能不能跑」：必须连整机一起量（2026-09-15 新增）

只报「模型占 5.9GB」是**误导性**的结论。同一台 16GB M1 Pro，模型占用不变，但体验可以从「流畅」到「卡死」——差别在**机器其余部分**。必须同时采这四项：

```bash
# ① 内存去向：wired 才是隐形黑洞（常态 2–4GB，>8GB 就该警惕）
vm_stat | awk '/Pages free/{f=$3} /Pages wired down/{w=$4} /compressor/{c=$5} END{pg=16384;
  printf "free=%.2fGB wired=%.2fGB 压缩=%.2fGB\n", f*pg/1073741824, w*pg/1073741824, c*pg/1073741824}'
# ② swap 水位（>80% 进危险区；满载说明内存已不够用）
sysctl vm.swapusage
# ③ 负载均值对比核数（8 核机器 load 10.5 = 超载 30%）
sysctl -n hw.ncpu; sysctl -n vm.loadavg
# ④ 谁在吃内存 + 进程总数（按应用聚合，找「同类开两份」）
ps -Ao rss,comm -m | head -25; ps -A | wc -l
```

**三条反直觉事实（本机实测）**

| 事实 | 数据 | 含义 |
|---|---|---|
| **卸载模型几乎不释放 free** | `ollama stop` 后 free 0.17→0.23GB，swap 只回收 16MB | Ollama 用 **mmap** 加载权重，卸载后页变成「可回收文件页」而非 free。**是弹性借用，不是霸占** → 用「关模型」来腾内存是无效操作 |
| **真正锁死内存的是 wired** | wired 9.20GB（占 16GB 的 57.5%），且卸载模型后反而涨（8.37→9.20） | 内核/GPU/驱动/长期运行累积，**只能靠重启回收**。16GB 机器上它决定「实际可用只剩 ~6GB」 |
| **瓶颈常是「同时开着」而非模型** | 583 进程：Chrome 21 + Safari/WebKit 38（双浏览器）+ 微信 23 + IDE + 网易云 | 优化顺序应是**先关同类冗余应用，再考虑模型** |

**正确表述方式**：不要问「模型多大」，要问「**机器还剩多少可动内存**」。
`可动 ≈ 16GB − wired − compressor`；实测该机可动仅 ~3GB，却仍能跑 5.9GB 模型 —— 因为 mmap + swap 在兜底，代价是负载升高。

**冷启动数据要区分两种**
| 场景 | 实测 | 说明 |
|---|---|---|
| 首次加载（页缓存冷） | **4.91s** | 模型文件需从 SSD 全量读入 |
| 卸载后重载（页缓存热） | **1.63s** | 文件仍在页缓存，几乎是瞬时 |
→ 报「冷启动 X 秒」时必须说明是哪种，否则两次测量会互相打脸。

## 1.6 Ollama 不给并发：加线程池调模型是无效优化（2026-09-15 实测）

| 方式（2 个相同请求） | 耗时 | 结论 |
|---|---|---|
| 串行 | 2.2s | — |
| 线程并发 | 2.1s | 省 5% = 噪声 |

**Ollama 服务端一次只算一个请求，客户端并发只会排队。**
→ 想给「本地模型管线」提速，**别写 LLM 线程池**。只有两条路：
①**缓存复用**（同输入不重算，最实在）；②**减少调用次数**（多个小任务合并成一次 prompt）。

**这条推论适用于整个管线**：优化前先按环节量耗时，并行只加在**纯 IO 等待**的环节上
（实测同一条视频管线里，TTS 网络合成占 39%、Pillow 渲染只占 3% —— 直觉会去优化渲染，
而真正该并行的是 TTS：0.17s/张的渲染全量才 2s，加线程池不值得）。

## 2. 最大的隐形开销：思考模式（think）

**qwen3 系模型在 Ollama 里不传 `think` = 思考默认开启。** 用户看到「模型好慢」，一半时间花在看不见的推理上。

必做的三行对照实验（同一 prompt，只改 `think`）：

| 配置 | 结果特征 |
|---|---|
| 不传 `think` | = 现网默认行为，可能隐式开思考 |
| `"think": false` | 快约 2 倍，输出 token 少 |
| `"think": true` | 最慢，思考字数最多 |

**结论不能只看速度**：关思考会掉质量——实测出现过句子碎片化，甚至**直接抄提示词里的 few-shot 示例**（首句变成示例原文原文）。所以：
- 面向人的文案 → 保留思考；
- 结构化抽取 / 分类 / 初筛 → 关思考；
- **无论哪种，都要把 `think` 显式写进配置**。依赖模型模板隐式默认 = 换模型/版本静默改行为，代码里看不出来（这是设计缺陷，不是调优）。

**M1 Pro 16GB / qwen3:8b Q4_K_M / Ollama 0.33.2 实测基线**
| 指标 | 值 |
|---|---|
| 解码速率 | 14.3–20.3 tok/s（硬上限，与输入长度无关；≈中文 600–700 字/分钟。系统高负载时仍达标） |
| 预填充 | 短问 88–385 t/s / 长文 1332 t/s |
| 冷启动 | **首次 4.91s** / **卸载后重载 1.63s**（页缓存热，见 §1.5） |
| 常驻内存 | 加载时 5.9GB / 16GB；**闲时进程仅 15MB** |
| 默认卸载 | 闲置 5 分钟自动卸载（`ollama ps` 的 `UNTIL` 列） |
| 首字延迟 | 关思考 0.12–0.79s；**开思考 27–67s** |
| 同任务耗时 | think=false 18.4s ｜ 不传 38.2s ｜ think=true 62.5s |

## 2.5 评估输出质量：方差比均值更重要（2026-09-15 新增）

**只跑一次就下结论 = 抽签。** 实测：同一提示词、同一模型（qwen3:8b），4 次采样得到 **3 种体裁**（合格绕口令 2 次 / 古诗写景 1 次 / 数数儿歌 1 次）。

**评估本地模型必须做的四件事**

| 做法 | 原因 |
|---|---|
| **同一任务采样 ≥3 次**，看的是**方差**不是最好那次 | 单次结果可能惊艳也可能跑偏，且用户看结果看不出来 |
| **记录耗时与质量的关系**，别假设"想得久更好" | 实测反例：6.7s（关思考）出最标准体裁；102.7s（烧 1624 token）出最机械的一次 → **更多思考 ≠ 更对，只是更长的自我说服过程** |
| **不要信模型自评** | 它自称"押韵、节奏感强"的那次实际写成了古诗。判断质量必须外置 |
| **约束写成可程序验证的硬形式** | 「数字 1–9 按顺序」→ 100% 守约；「押韵、有节奏感」→ 跑偏成古诗。**主观形容词 → 跑偏；可验证硬约束 → 守住** |

**由此推出的管线设计（适用于任何本地模型批处理）**
1. **N 选 1**：同输入生成 3 版 → 规则打分或人工挑 1 版。本地推理零成本，代价只是耗时 ×3。
2. **校验外置**：门禁用确定性规则（句数/字数上限、关键词命中、禁用词），**不要「让 AI 检查 AI」**。
3. **提示词写死硬约束**，把可量化的边界（`≤12 句`、`每句 ≤20 字`、`必含 keyword`）写进 prompt。

**另一个易忽略的变量：上下文污染。**
同一模型写创意任务，若会话前半段全在聊技术名词（资源/模型/部署），产出会退化成干巴巴的罗列（实测退化成"数数儿歌"且序列错乱）。
→ **创意任务另起干净会话**，别和长技术对话混在一个 session。这不是模型问题，是会话卫生问题。

## 2.6 本地小模型能不能做 Agent（2026-09-15 实测，含反直觉结论）

**先纠正三个高频误判**（用户问「有多会话管理吗 / 模型咋接的记忆 / 要调工具得上框架吗」时）

| 误判 | 事实 |
|---|---|
| 「模型有记忆」 | **零记忆**。模型是无状态函数 `f(tokens)→tokens`，每轮把 messages 数组**全量重发**。实测：清空 history 后问「我刚才让你读了哪个文件」，它答不出，而且**编造**了「你刚才让我读取了一个文件」——用幻觉填补记忆空白 |
| 「模型自述能力可信」 | 不可信。抓包实测：它自称「我有 7 种能力：回答问题、文本创作、编程帮助…」——这不是能力清单，是**权重里的自我描述幻觉**。同理它会把自己说成「由通义实验室开发」，与真实运行环境无关 |
| 「调工具必须上框架」 | **不必须**。Ollama `/api/chat` 原生接受 `tools` 字段（OpenAI 同形 JSON Schema），模型直接返回 `message.tool_calls`。实测 qwen3:8b 单步调用 **4.9s** 返回 `{"function":{"name":"read_file","arguments":{"path":"/etc/hostname"}}}`，**零框架、零依赖、只用标准库** |

**Agent loop 的最小骨架（约 100 行，手搓即可）**

```
组装 messages（system + 工具声明 + 历史 + 本轮）
  → POST /api/chat 带 tools
    → message.tool_calls 非空？
        否 → 收工
        是 → 你执行工具 + 校验输出 → role=tool 回灌 → 回到上一步
```

**职责边界**：Ollama 只负责「模型前向」这一段；组装、分叉判断、执行回灌**全是你的代码**。
框架（LangGraph / OpenAI Agents SDK / smolagents）能省的是组装样板，**省不掉 loop 的可靠性**。

**⚠️ 8B 模型 loop 的真实失败模式（框架不帮你兜）**

实测同一场景（工具返回错误）**两次表现不一致**：
- 一次：把错误字符串当"有效文本"传给了下一个工具（`count_words("读取失败：Errno 2…")` → 报"共 57 个字符"），然后**收工交付**，把失败当成功；
- 另一次：正确报告「目录不存在」。

→ 结论：**小模型的 loop 终止判断不可靠，且不稳定**（与 §2.5「方差比均值重要」同源）。
→ 必做三件事：①**工具输出规范化**——错误只回 `{"ok":false,"error":"..."}`，别把原始异常文本丢进去；②**外置门禁**——交付前用确定性规则校验（文件存在？字数在范围内？），不通过就打回；③**步数上限**——硬闸，防止绕圈。

**4K 上下文是硬约束，决定了「该不该用框架」**

qwen3:8b 默认 ctx 4096。框架自带的 system prompt + 工具描述 + 重试历史会**吃掉本就稀缺的额度**，
留给用户素材的可能不到一半。**本地小模型场景下，轻量手搓通常优于引框架**。
（想抄设计就读 smolagents 源码——核心约 1000 行，Apache-2.0，原生支持 Ollama，Python ≥3.10。）

**skills 的渐进式披露（省 token 的核心设计）**

不要把 skill 全文塞 system prompt。正确做法：
1. system prompt 里只放 **`name` + 一句话 description** 的索引（20 个 skill × 30 字 ≈ 600 字，常驻很便宜）；
2. 模型判断需要时调 **`load_skill(name)`** 工具读全文（贵，但只在真需要时付）；
3. 索引长到塞不下时，再加 **`search_skills(query)`** 先搜后 load；
4. 4K ctx 下**一次最多 load 1 个全文**，用完要能卸载。

**多会话最小实现**（判断某网页台「有没有多会话」看三点）
① 有没有 `sessions` 集合（而非单个 `history` 数组）；② 有没有落盘（`localStorage` / 服务端文件）；
③ 刷新后能否恢复。只满足①②③中的部分 = 假多会话。

## 3. 零安装网页界面（关键事实：CORS 放行 localhost）

**先验事实再动手**（别猜）：
```bash
curl -s -i http://localhost:11434/api/tags -H "Origin: http://localhost:8123" | grep -i access-control
```
只要看到 `Access-Control-Allow-Origin: http://localhost:8123`（回显），就说明**任意 localhost 端口的网页都能直连 Ollama，零配置**。

**但有个必踩的坑**：`file://` 打开页面的 Origin 是 `null`，不在白名单 → 请求被浏览器拦掉。
**所以必须经 `http://localhost` 起服务**，不能双击 HTML：
```bash
python3 -m http.server 8123 --bind 127.0.0.1 &
open "http://localhost:8123/ollama_webui.html"
```
（要显式白名单时用 `OLLAMA_ORIGINS=https://foo.com ollama serve`。）

**单文件网页台该有什么**（零依赖即可，17KB 够用）：
1. `/api/tags` 拉模型列表填下拉框；
2. `/api/chat` + `stream:true` 流式输出（手动按 `\n` 切 NDJSON）；
3. **实时性能面板**——从 final chunk 读六个字段，实时显示 TTFT / 解码 t/s / 预填充 / 加载 / tok 数；
4. 参数：`temperature`、`num_predict`、`num_ctx`、`think` 开关；
5. **「卸载模型」按钮**（`POST /api/generate {model, keep_alive:0}`）——16GB 机器上非常实用；
6. `AbortController` 做「停止」。

**页面代码两个易错点**
- 定时刷新模型列表（`setInterval`）会**把用户已选中的模型重置回第一项** → 刷新前记住 `sel.value`，刷新后若仍存在则还原。
- 默认让思考开关**关**，首字 0.2s 的体感远好于 30s。

## 4. 无头验证本地网页的坑（会白白卡住十几分钟）

| 现象 | 原因 | 解法 |
|---|---|---|
| `--dump-dom` / `--screenshot` 永不返回 | 页面里的 `setInterval` 持续发请求，Chrome 的 virtual time 被挂起的网络请求冻住 | 去掉轮询做测试副本，或**改用 CDP**（推荐） |
| `--virtual-time-budget` 对流式响应不可靠 | 虚拟时间不随流式 chunk 推进 | 同上 |
| Chrome headless 在 macOS 沙箱内起不来 | 沙箱限制 | 加 `--no-sandbox --disable-setuid-sandbox` |

**可靠做法：CDP + Node 内置 WebSocket（Node ≥22 自带，无需装包）**
1. 起 Chrome：`--headless=new --remote-debugging-port=9222 --user-data-dir=/tmp/xxx <url>`
2. `fetch http://127.0.0.1:9222/json/list` 找 `type==="page"` 的 target
3. `new WebSocket(target.webSocketDebuggerUrl)`，用 `Runtime.evaluate`（`awaitPromise:true`）轮询 DOM，
   条件满足后 `Page.captureScreenshot` 存图。
4. 这样能**同时拿到「真实回答 + 指标渲染 + 控制台异常数」**，比只看 DOM 强得多。

## 5. 排查顺序（照这个走，少绕路）

1. `ollama list` / `curl :11434/api/tags` → 模型在不在、服务活不活
2. `ollama ps` → 是热的还是已被卸载（决定要不要单测冷启动）
3. **整机资源四连采**（§1.5）→ wired / swap / load / 进程数，先判断「瓶颈在模型还是在机器」
4. 分列预填充 / 解码 → 判断瓶颈在输入还是输出
5. 三行 think 对照 → 排除「隐形思考税」
6. 看 `think=false` 的**输出内容本身**，别只看速度 → 确认质量能接受
7. 要界面 → 先 curl 验 CORS，再上单文件网页；别一上来装 Open WebUI

## 6. 反面清单

- ❌ 用墙面钟时间当「模型速度」——里面混了加载、排队、TTS、IO。
- ❌ 只看平均 tok/s，不看 TTFT——流式场景里用户感知的是**首字延迟**。
- ❌ 发现「关掉思考快 2 倍」就全局关掉——质量会掉，先看输出。
- ❌ 硬编码 `qwen3:7b` 这类标签——**不存在的标签**会让命令静默失败（本机实测标签是 `qwen3:8b`）。
- ❌ 一上来装 Open WebUI（≥1GB）/ 官方桌面 App（可能与 brew 版抢 11434 端口）——先试零安装方案。
- ❌ **用「卸载模型」来腾内存**——实测 free 只涨 0.06GB、swap 只回收 16MB（mmap 机制）。想腾内存该关的是**冗余浏览器/IDE**，不是模型。
- ❌ **只报「模型占 X GB」就下「这台机器够不够」的结论**——必须连 wired/swap/负载一起量。同一台机器，瓶颈往往在模型之外。
- ❌ **跑一次输出就给模型下质量结论**——4 次采样可能出 3 种体裁，单次结果既可能是精品也可能是废品。
- ❌ **相信模型的自我评价**（"押韵、节奏感强"）——它自评与事实经常不符，质量判断必须外置。
- ❌ **以为模型「记得」上一轮**——它零记忆，记忆全在你重发的 messages 里。清空历史后它不但答不出，还会**编造**「你刚才让我…」来填空白。
- ❌ **信模型的自我能力描述**——「我有 7 种能力」是权重幻觉，不是能力清单，更不是你的工具清单。
- ❌ **为了调工具就去引 Agent 框架**——先试 `/api/chat` 原生 `tools`（~100 行手搓）；4K ctx 下框架的样板提示词会挤掉你的素材。
- ❌ **把工具原始异常文本直接回灌给模型**——8B 会把报错当有效结果继续往下传，最后**把失败当成功交付**。错误必须规范化成 `{"ok":false,...}`。
- ❌ **只靠模型自己判断「任务完成了吗」**——实测同场景两次行为不一致。交付前必须有确定性门禁。
- ❌ **把 skill 全文塞进 system prompt**——索引常驻（便宜）+ `load_skill` 按需读全文（贵但少付），才是省 token 的正解。
