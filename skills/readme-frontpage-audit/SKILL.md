# README 门面体检与拆读者重构

## 什么时候用

- boss 说「这个 README/文章看着奇怪」「引用块好多」「这些总结/我是谁/目录是不是没必要」
- 开源前的门面自查
- 任何「这份文档要给别人看，但现在是给自己写的」的场景

**不要**（超出本 skill 范围）：纯技术文档改写、公众号文章去 AI 味（走 `de-ai-flavor`）。

---

## 核心洞察（先读这段，它决定了改得对不对）

**README 看着奇怪的真正病因，十次有九次不是「内容太多」，而是「一个文件服务了两个读者」。**

- **访客**（路过的人）：关心 干什么 / 怎么装 / 跑起来什么样
- **维护者**（自己和下一个人）：关心 目录结构 / 为什么这么设计 / 去看哪篇 doc

两类内容混装，结果两边都不讨好：**访客在第一屏拿不到「怎么装」，维护者觉得理念讲不透。**

三个高频症状，要分开治，**不能一刀切全删**：

| 症状 | 是不是真问题 | 判据 |
|---|---|---|
| `>` 引用块多 | ✅ **是** | 分发型头部项目普遍 <1% |
| 「为什么这么设计 / 我是谁」章节 | ❌ **不是** | ripgrep 有 45 行 `Why should I use ripgrep?` |
| 目录结构 tree 占篇幅 | ✅ **是**（最该砍） | 头部项目没有贴完整 tree 的 |

**最关键的一条**：要改的是**形式**（灰块旁白 → 列表/正文/表格），不是**删掉骨头**（差异化卖点）。
一个 README 把「零成本 / 断网 / 隐私」这类唯一差异化删掉，就退化成千篇一律的安装说明。

## 六步流程

### 1. 备份（铁律，先于一切）
```bash
cd <repo> && cp README.md ~/.backups/README.md.before-frontpage-rework
```
优先走工作区自带安全脚本（如 `tools/safety/backup-before-op.sh`）。同时确认 `git status` 基线。

### 2. 抓头部同类项目做**实测**对比（不许凭感觉）
选 6–8 个**同性质**的项目（同为「本地工具 + 有人要装」就别拿框架去比）。

```python
import subprocess, base64, re
for repo in ["ollama/ollama","yt-dlp/yt-dlp","ggml-org/whisper.cpp","BurntSushi/ripgrep","junegunn/fzf","sharkdp/fd"]:
    out = subprocess.run(["gh","api",f"repos/{repo}/readme","--jq",".content"],
                         capture_output=True, text=True, timeout=25)
    lines = base64.b64decode(out.stdout.strip()).decode("utf-8","ignore").splitlines()
    n = len(lines)
    q = sum(1 for l in lines if l.lstrip().startswith(">"))
    inst = next((i for i,l in enumerate(lines,1) if re.search(r"^#+\s.*(install|安装|quick ?start|usage)", l, re.I)), None)
    print(f"{repo:28} 行{n:5} 引用块 {q/n*100:5.1f}%  首个安装/用法 {'第'+str(inst)+f' ({inst/n*100:.0f}%)' if inst else '无'}")
```

> ⚠️ `gh` 常不在窄 PATH 里 → 用 `export PATH=/opt/homebrew/bin:$PATH`。
> ⚠️ `inst` 可能为 `None`，先判空再除法（`TypeError` 坑，实测踩过）。

**按性质分组看，别混着平均**：分发型（ollama/yt-dlp/whisper.cpp）引用块 <1%；
功能展示型（fd/fzf）4–7% —— 拿哪个对标取决于你的项目用户是「来装」还是「来看功能」。

### 3. 自测：把 README 按「对谁有用」拆开
```python
# 统计：引用块行 / 目录树行 / 自述章节行 → 占全文 %
# 并把每处引用块打标签：导航旁白 | 警示 | 口号 | 其他
```
**导航旁白**（「想去搞明白看 doc/xx」）是最该删的一类 —— 它是对维护者说话的语气。
**警示**（已知缺口、合规红线）要保留但改形式，别用灰块（诚实披露是好东西）。

### 4. 验证 / 推翻 boss 的直觉
老板的感觉通常**半对**。必须明确说出哪一半对、哪一半反对，并拿反例证据：
- 「唉，这些总结该删」→ **但 ripgrep 有 45 行 Why 章节** → 改形式，别删
- 「引用块看着乱」→ **对，7.7% 是最高的** → 砍到 0

**不要唯上。** 全按指令删骨头，等于把唯一差异化扔掉。

### 5. 重装结构（推荐动线）

```
H1 + 一句 slogan（不用引用块）
一句话它是干什么
GIF / 截图
实测数据表            ← 用表格，别用引用块
## 30 秒：装好就用     ← 关键：从第 2 屏就能开始动手
## 快速开始（开发者）   ← 可复制代码块
## 为什么不一样        ← 差异化压缩到 3 条 + 一行指向完整版
## 全链路成本表
## 深入阅读（指针表）   ← 目录树下沉后的入口
## 状态与协议
```

砍掉的维护者内容下沉到 `AGENTS.md` / `CONTRIBUTING.md`，README 只留一行指针。

### 6. 机检（必须，不能目测）

```python
# ① 本地链接逐个 exists() —— 写了路径 ≠ 文件存在（本项目血泪教训）
# ② 相对旧版：]\(...) 链接零丢失 + doc/ 提及零丢失
# ③ 关键命令 / 关键数字逐条比对在存
# ④ 复核指标：行数、引用块 %、"怎么装"位置 %
```

---

## 反直觉 / 坑

| 坑 | 说明 |
|---|---|
| **别删 Why 章节** | ripgrep 45 行 `Why should I use ripgrep?` + 22 行自曝短板，是公认标杆。改引用块形式即可。 |
| **别一刀切按引用块删** | 「用引用块写的旁白」该删，「表达了什么理念」不该删 —— 区分形式与内容。 |
| **目录结构 tree 是最大肥肉** | 常占 25–30% 篇幅，对访客零价值 —— 删除优先级高于引用块。 |
| **别把已知缺口一起删掉** | 诚实披露是好东西（这个项目尤其看重）。挪出灰块、压缩成 ⚠️ 一行或表格行即可。 |
| **「深入阅读」表会漂** | 手维护，新增 doc 会漏登记 → 正文注明「完整索引以 doc/README.md 为准」。 |
| **安装位置比行数重要** | 目标是让访客在第 2 屏（约 15–20% 处）就能动手。 |

## 交付前的自检一句话

> 改完请回答：**路过的人在第 2 屏能不能开始动手？下一个人能不能在 README 里找到项目的核心理念？**
> 两个都答「能」才算过 —— 只答对一个，说明还是混装。
