# 项目对外总览白皮书 SOP

> 目标：让一个**没参与过这个项目的人**，在 5 分钟内搞明白
> ①它是什么 ②怎么搭的 ③为什么这么搭 ④跟同类比哪里不一样 ⑤凭什么别人抄不走。
>
> 与 README 的分工**必须在文首写明**：README = 30 秒速览，本文件 = 5 分钟纵深。
> 否则会被质疑"跟 README 重复"。

## 零、先核实，别写观点

**动笔前做的事**（这一步省不掉）：

1. **先搜仓库**：已有结论很可能写过（本次 `doc/07` / `doc/11` / `doc/12` 早已有差异化与产品化内容）。
   写新文档前先 `grep`，否则就是造重复副本。
2. **抓硬事实**：模块数 / 行数 / 实测数字 / 依赖清单，用命令实测
   （`wc -l` / `du -sh` / 项目自带 bench 工具），**不引用记忆里的数**。
3. **判形态**：
   - **工程记录类**（架构 / 自述，会随代码演进、需要 diff）→ **MD**
   - **决策 / 分析类**（选型对比、路线建议，给人读）→ **HTML 看板**

## 一、五段结构（按此顺序写）

### §0 扫盲 —— 最容易漏、价值最高的一节

**为什么必须有**：技术文档体系有个系统盲区 —— **每一篇都假设读者已经懂了**。
写的人懂，所以看不见这个缺口。外人读到第三句就走不下去了。

**做法**：
1. 把文档里出现的**专业名词逐个列出来**，问：**"哪个词没有任何一处解释它？"** → 那就是缺口。
2. 名词必须**分层**，不是并列罗列。例（本地 AI 场景）：
   - 运行时（Ollama）→ 模型家族（Qwen3）→ 具体权重（`qwen3:8b`）→ 量化格式（Q4_K_M）
   - 类比：**播放器 / 片名系列 / 某一部影片 / 压缩格式**
3. **最有用的是"分诊表"**，不是定义表 —— 让读者能把"症状"映射到"该修哪一层"：

   | 用户会说 | 真实病因 | 该动哪层 |
   |---|---|---|
   | 连不上 / 找不到 | 运行时没起 / 权重没下 | 有确定答案，查配置 |
   | 答得不好 / 格式乱 | 模型能力 / 提示词 | 要实验 |

   **一句话判据：把"有确定答案的问题"与"要实验的问题"分开** —— 混在一起，
   读者会做「答得不好 → 重装运行时」这种白费功夫的操作。
4. 顺手记一条**反直觉洞见**（本节的记忆点）：例「同一份权重换个运行时，默认行为会变
   —— 因为默认参数是运行时模板给的，不是模型属性」。

### §1 架构 —— 一张图 + 分层归位

- **数据流图**用 ASCII（零依赖、任何渲染器都稳、可 diff；不依赖 mermaid 渲染）。
- **每个环节标注"是否用模型"** —— 若架构哲学是"少用模型"，这张表就是证据。
- **分层解耦表**（内核 / 二进制 / 壳 之类），并回答一个高频问题：
  「要支持多平台，是不是得重写架构？」
- 模块按层归位，**指出"塔尖模块"**（被所有人依赖、自己不依赖任何人）与
  **"唯一装配点"**（加新 provider 只改一处）。

### §2 理念 —— 必须能指到文件

**铁律：每条理念都要能指到一个文件 / 一行配置。** 指不到的就是口号，删掉或降级。

列成表：`理念 | 一句话 | 落在哪里（可核证据）`。

并**点出理念之间的张力** —— 有张力的体系才可信：
> 例：「优先复用」（油门）与「克制」（刹车）方向相反，后者是刻意补的反向闸 ——
> 只有前者，就成了"一条只能踩油门、不能刹车"的规则。

### §3 差异化 —— 必须写「主动放弃了什么」

- 竞品表**标注快照日期**（星数会变，引用前重拉），并**写明与项目内竞品文档的分工**（谁速查、谁论证）。
- 三条**结构性**差异（不是"我们更好"，是"我们选了另一条路"）。
- **必带「主动放弃清单」** —— 写明放弃什么、为什么、代价是什么。
  只写优势的是宣传稿，读者会自己发现缺失然后不信你。

### §4 护城河 —— 先认账，再立论（见下节框架）

## 二、纸护城河评估框架（本 SOP 最有复用价值的部分）

**顺序很重要：先列"看起来像壁垒、实际不是"的，再列真的。先认账才有说服力。**

| 类别 | 判据 | 例 |
|---|---|---|
| **纸护城河** | **能在一周内被熟练工程师照文档重写** → 就不是壁垒 | 代码本身 / 架构设计 / 可公开下载的资产 / idea（看同赛道星数即可证伪） |
| **真护城河** | 是**判断力**或**累积型资产**，不随代码被带走 | ①方法论（判断力）②错题库 + 实测数据（**时间成本不可压缩**）③内容资产与人设 |

**关键推论**（很多人绕不过来）：
> 既然代码是纸护城河，**开源它就不损失真资产** →
> 「引擎开源 / 产品与品牌保留」这个分层是**按壁垒在哪来切，不是妥协**。
>
> 这条把"技术拼装不是护城河"从一句口号变成**可检验的评估**。

**必带 §脆弱点（自我对抗）**：列出最脆的一环、能力天花板、维护单点、平台依赖。
> **不列脆弱点的护城河评估是宣传，不是评估。**

## 三、收尾

1. **对账纪律**：总览是**结论的副本**（不含独立论证）→ 天然会漂移。
   必须在项目索引里写明：**改上游文档结论时，回头看总览有没有跟着漂移**，
   并点名最容易漂的几处（架构图 / 理念表 / 竞品表）。
2. **指针反指**：让上游文档（如竞品文档）反向声明与本总览的分工，**双向写**才防漂移。
3. **数字口径页脚**：每个数字注明出处命令与实测日期。
4. **脱敏自查**（对外内容必做）：扫绝对路径 / 真实姓名 / 雇主名 / 内部代号，**零命中才算完**。

## 四、常见坑

| 坑 | 症状 | 修法 |
|---|---|---|
| 写成 README 复述 | 读者觉得"这不就是 README 吗" | 文首写明 30 秒 / 5 分钟分工；总览只写 README **没有的纵深** |
| 扫盲节只罗列定义 | 读者还是不知道自己遇到的情况该改哪 | 用**分诊表**（症状 → 病因 → 该动哪层）代替定义表 |
| 理念写成口号 | 每条都像正确的废话 | **强制要求每条能指到文件**；指不到的删 |
| 只讲优势 | 读者自己发现缺失后不再信任 | 加「主动放弃清单」+「脆弱点」两节 |
| 护城河写成自夸 | 没有可证伪的判断 | 用纸/真二分；**先承认代码不是壁垒** |
| 总览与上游文档各说一套 | 多处副本静默漂移 | 双向指针 + 对账纪律写进索引 |
| 写新文档前没搜仓库 | 造出重复副本 | **动笔前先 grep**；已有的原地补节，不新建 |
