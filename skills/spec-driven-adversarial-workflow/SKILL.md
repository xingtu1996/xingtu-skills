# Spec 驱动 × 对抗式审查工作流

> 适用：**维度多、耦合重、涉及既有系统改造**的任务。判断口诀——「这活儿会不会改到别人的字段/口径/引擎？」会，就走本流程；不会，普通直接执行即可，别过度设防。

## 适用性守卫（工作区无关，先自证）

本技能是**纯方法论**，不承载任何工作区的私有路径、凭据或数据口径。开工前只做两件事：

1. **确认任务复杂度门槛**（见上方判断口诀），不满足就退出，不为了仪式感跑全程。
2. **探测本工作区惯例**：有无 spec 脚手架引擎、有无时间轴留痕工具（CHANGELOG 类）、有无备份/安全删除脚本、有无 SSoT 登记文件。探测到 → 用本区惯例（行途空间的具体命令清单见 `reference.md` §附录A）；探测不到 → 降级模式：spec 落 `specs/YYYYMMDD-名称/`（或本区等价目录），留痕写一份 `决议记录.md` 并在交付回复中列明落盘路径。公司侧/新项目空间可直接使用，零私人信息注入。

## 六阶段流程

### Step 0 · 地基侦察（不拍脑袋）

1. 派**侦察子代理**（Explore / general-purpose，大 token 检索隔离在子上下文，只回简报不回文件 dump）。
2. 侦察清单：任务涉及的**既有引擎与机读字段**（打分/信号/数据源叫什么、在哪、字段真名）、脚本产出物、台账现状、spec 命名惯例（有无 scaffold 引擎）、红线与坑。
3. 产出「事实地基」小节，**显式区分用户口头假设与实测事实**——不符时以事实改写问题定义，并在 00 总纲注明"侦察后修正"。
4. 典型修正：口头说"要设计一个综合研判引擎"，实测发现打分引擎已存在 → 真问题变成"缺编排与执行闭环"。**侦察结论直接决定 00 的复用地图。**

### Step 1 · 建 Spec（四件套）

- 目录：有 scaffold 引擎先跑引擎（如行途 specs-engine：分钟级前缀防多 agent 撞车、自动加索引行），**有引擎用引擎，不手搓目录**；无引擎则 `specs/YYYYMMDD-名称/`。
- `00_README.md` 总纲必含六节：一句话 / 真问题（侦察后修正）/ **复用地图**（引用既有资产路径，不复制正文）/ 缺口 / 红线与坑 / **待决策拍板表（每项带默认值，未回即按默认执行，不阻塞往下写）**。
- `01_任务分解与依赖DAG.md`：降维分层 **G0 地基 → G1 核心 → G3 收敛**，每层标并行度与"可独立验收"判据（写"怎么算完"，不写"做了啥"）；跨层依赖画明。
- `02_决策模型.md`（或设计/字段级细节）。
- 改任何**既有文件**前先备份（本区备份惯例；无则复制为 `*.bak` 到备份目录）。

### Step 2 · 红队对抗（独立上下文 × 多视角 × 两轮）

> 单一带五类靶的红队容易"要么全信、要么淹没在误报里"。这里升级为**多视角并行攻击 + 脚本交叉验证 + Filter 减法**——三条关键增量：① Round 2 用脚本判真伪、不请"LLM 法官"；② 多视角含 Filter 拦截 30-50% 误报；③ 发现用**原文片段定位**不用行号。（方法论蒸馏自成熟工程对抗审查体系，此处只取通用部分、工作区无关。）

**Round 1 · 多视角并行攻击（3 个互不可见的独立上下文子代理）**，防自查盲区与群体思维，各扫同一 spec：
- **怀疑论者（Refuter）**：结论证据充分吗？样本量够吗？有无遗漏成本 / 未标"待验证"的假设？（打"单一信号绑架"）
- **审计员（Auditor）**：spec 引用的每个字段名/路径/小节，实地 `ls`/`grep`/`test -e` 核对是否真实存在、跨文件口径与数字是否自洽。（打"引用证伪 / 口径污染 / 副本腐烂"）
- **优化者（Optimizer）**：新组件是否与既有引擎重复造轮子、能否降级为"喂数/挂接"而非新建？有无更简方案。（打"平行系统"）

> **五类靶**（引用证伪 / 单一信号绑架 / 平行系统 / 口径污染 / 副本腐烂）是三条视角共同的攻击面清单，不变；prompt 模板见 `reference.md` §1。
> 每视角发现上限 ~7 条（太少=草率，太多=噪音），每条**必带具体证据**，无证据的主观偏好不上报。

**Round 2 · 脚本交叉验证 + Filter 误报拦截（关键：交叉验证用脚本，不用"LLM 法官"）**：
1. **去重定级用脚本**，不再请一个 LLM 当终审法官（既省一轮法官 token，又避免法官自身引入新幻觉）：把三份发现按"引用位置/原文片段"归并——同一处 **≥2 视角独立命中 = ✅ 高置信**，仅 1 视角命中 = 🔹 单独。
2. **审计类发现仍走脚本复核**：路径存在性 `test -e`/`ls`、字段/口径 `grep`、数字跨文件自洽 `grep`——由机器判定，不靠模型复述。
3. **Filter（第四职责，可并入任一视角或主会话）对 🔹 单独发现逐条做减法**：无具体证据 / 纯风格偏好 / 表述模糊 → 标 `[已过滤]`。**目标拦截 30-50% 低质量发现**减轻人审负担；**Filter 只减不增、不改写发现内容**。

**定位规范（治"AI 报的行号对不上实际"经典病）**：红队引用问题**不写行号**，写**可 grep 的原文片段**（spec 里那句话 / 那个字段名 / 那个小节标题）+ 文件路径。接收方用 `grep` 片段定位；片段匹配不到再全文扫，仍失败标"需人工定位"。三级定位：① 片段 grep ② 全文相似扫描 ③ 人工确认。

红队（含 Filter）**只攻击 + 只做减法，不处置**；成立/不成立与怎么改的判断归主会话 Step 3。

### Step 3 · 修订收口（03 + 指针 + SSoT 表）

1. 写 `03_对抗式审查与修订.md`：逐条「红队发现 → 成立/不成立 → 证据 → 处置」，**对 00/01/02 有推翻力**；不成立项也要写理由，不许静默丢弃。
2. **给 00 顶部挂指针**：`⚠️ 以 03 为准（冲突处推翻本文件）` + 一句话列举被推翻要点——防 00/03 内部双份腐烂。
3. 若发现口径散落，产出「单一 SSoT 表」：什么口径 → 唯一权威落点 → 其余处只引用不复制。

### Step 4 · 留痕（收尾即交接）

- 回写本工作区时间轴（行途：`changelog_append.py --tool <本工具身份>`；见 `reference.md` §附录A；无时间轴工具则 `决议记录.md` + 交付回复列路径）。
- 若本区有技能/资产台账脚本，同步重生。
- **完成判定查落盘凭证**（spec 文件存在、时间轴新行、mtime=今天），不问模型自述。
- 向决策人汇报：三五行 recap（真问题怎么修正的 / 红队推翻了什么 / 挂着哪几个待拍板默认值），不翻历史。

### Step 5 · 执行委派与磁盘核对验收（定稿放行后）

> Step 0–4 解决「方案靠不靠谱」，Step 5 解决「执行有没有真落地」。spec 定稿并经决策人放行后，各 Phase 走**后台委派执行 + 主代理独立验收**——执行者的自述不作数，完成判定只认磁盘凭证。

1. **放行闸门**：决策人明确放行（如「全按默认放行」或逐项拍板）才进本步；未放行只交 spec，不跑代码、不改工作区文件。
2. **委派简报必须自包含**（每 Phase 一个后台执行子代理，四要件缺一不可）：
   - ① **唯一真相源 = 定稿 spec 目录**（列明文件清单与「冲突以此为准」；有多个 Phase 时要求**先读执行日志尾部**，不重做已完成工作）；
   - ② **工作区红线在 brief 内复述**（改前备份、禁硬删、只读/不发布等），不依赖上下文自动注入——子代理可能运行在别的工具会话里；
   - ③ **辖区与排他**：指定工作目录与可改文件范围；多路并行委派时各划辖区，**并发共改文件默认互斥**，共享留痕文件走带并发保护的追加脚本；
   - ④ **DoD 写成机器可验证**：完成自述前须 `ls`/`grep`/实跑工具自证；不许虚报，没做完或超出辖区的写成「尾巴项」如实上报，不擅自扩大动作。
   - ⑤ **交接物必须"填空即用"**（self-contained-handoff-prompt 精神，2026-09-16 并入）：凡交付给**别的 agent 或人**的执行提示词，所有路径/包名/参数**预先解析填好**，只留真正需对方提供的空位；禁"口头描述+接收方自己再研究"的半成品（实测纠偏："提示词直接填好路径再发我"）。多路并行 fanout 时另挂 `fanout-mainline-ledger` 单一主线台账（登记/核销/丢失告警），主线状态只从台账答。
3. **主代理磁盘核对验收（不轻信自述——模型把没做的事说成做了是高频幻觉）**：完成通知后**不读全量大日志**，直接对磁盘产物逐项核验——
   - **实跑**产物工具/脚本一次，确认输出真生成、关键产物 mtime=当天；
   - **grep** 关键字段与任务清单勾选（勾选须与磁盘事实一致，防「说了做了但没勾」与「勾了实际没做」两个方向）；多池/多副本镜像用 `diff -q` 验字节同源；行为门禁（hook/validator）正反面例实测拦截与放行；
   - 核验落空**先疑自己的探针口径再下结论**：键名/路径对不上时先打印产物真实结构核对，别把「探针写错键名」误判成「它没做」（实测坑：`track_c` vs 真实键 `track_c_decay`）；
   - 红线越界核查：有无碰辖区外文件、擅提交、擅发布。
4. **收口**：验收通过才刷新进度看板/任务勾选（看板产物默认本地文件，决策人未明确要求不上网络）；汇报三五行 recap——落了什么+凭证、留了什么尾巴（区分「按分期的诚实尾巴」与「虚报」）、下一 Phase 入口。简报模板与核验命令套路见 `reference.md` §5。

## 核心纪律（红线）

1. **不重造已存在的打分/信号引擎**——本流程产出的是编排 + 执行闭环，不是第二套决策系统；红队指认平行系统时优先"降级为喂数/挂接"而非"新建"。
2. **待拍板必须带默认值**，禁开放式问题占决策人带宽（≤2 个 A/B 选择题）。
3. **03 推翻 00 后必须挂指针**，否则就是新的双份腐烂。
4. 侦察与红队子代理**只读**；写操作只发生在 spec 目录与本区留痕登记处，且改既有文件前先备份。唯一例外：Step 5 的**执行子代理**可在 brief 划定的辖区内写，辖区外零动作、越界项只上报不擅动。
5. **交叉验证用脚本不用"LLM 法官"、发现用原文片段定位不用行号**——这是 Step 2 的效率与精度双保险：脚本判真伪省一轮法官 token 且免法官幻觉，片段定位治"行号漂移对不上"。
6. **定稿放行后的执行，验收认磁盘不认自述**（Step 5）：委派前 brief 自包含（真相源+红线复述+辖区+DoD 自证），完成后主代理实跑工具 / grep 关键字段与勾选 / diff 镜像独立核对，验收通过才刷新进度看板；核验落空先疑自己探针口径，别误判执行方没做。
7. **对外断言先过"可证伪闸门"**（falsifiable-claim-gate 精神，2026-09-16 并入）：交付/文案/spec 里任何"能做什么·有多快·完全离线·零损耗·已通过 X·100% 覆盖"式承诺，落笔前先设计一个**能失败的实测**并如实取数；结论只允许 **为真 / 为假 / 条件成立（注明已知缺口）** 三态，用真实数字替换会被打脸的口号——实测跑不了的断言要么改文本、要么显式登记缺口，绝不靠形容词自证。（与第 5/6 条同源：第 5 管方案结论、第 6 管执行验收、本条管"嘴上对读者说的每句话"。）

## 与相邻能力的边界

| 相邻 | 分工 |
|---|---|
| 稿件/文章审查类技能（如行途 `adversarial-review`） | 审**内容成品**；本技能审**方案/设计/spec** |
| 多任务并行编排类（如行途 `xingtu-orchestrate` / workflows/06） | **执行期**编排；本技能管**立项期**，产出的 01 DAG 可交棒给它跑。Step 5 只承载「单 Phase 后台委派 + 磁盘验收」最小闭环；多路并行深度编排（依赖调度、并发闸门）若工作区有执行期编排技能归它，两边不双份维护 |
| 发布/上线前核验类技能 | 单篇单版闭环；不涉 spec |
| 故障诊断（investigate-first 语义） | 现象→根因；本技能 Step 0 侦察含其精神但面向立项 |
