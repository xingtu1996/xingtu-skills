# 并行开发的工作树隔离（Worktree Parallel）

> **定位**：这是 `specs-engine`（SDD + sub-spec 机制）在**执行层**的一个实践补位——specs-engine 管「把需求固化成可继承的 Spec」，本技能管「Spec 定了之后，怎么让 2+ 执行体真并行而不互相踩」。
> **设计原则**：**工具非依赖**。第 1~5 节是纯 git + 通用工程判断，任何 CLI 都能用；第 7 节只做工具适配映射。

---

## 一、判据：先问「文件级切分能不能切开」（最重要）

**不要一上来就开 worktree。** 按序问：

| 序 | 问题 | 答案 | 动作 |
|---|---|---|---|
| 1 | 两批改动落在**完全不相交的文件集**吗？ | 是 | **不要开 worktree**。同工作区、按文件分工即可，零成本、零合流 |
| 2 | 有重叠文件，但**重叠文件归一方独占**（另一方跳过）吗？ | 是 | **不要开 worktree**。按文件指派，重叠文件指定唯一 owner |
| 3 | 重叠文件**无法归一方**（双方都要在同一文件里改）吗？ | 是 | **才开 worktree**，且**必须预留合流对账**（见 §三-D） |

**「开 worktree 免冲突」是错觉**：worktree 只解决*并发写同一文件时后写覆盖前写*（工具级问题），**不消除 git 层的冲突**——它把冲突从「写入期」推迟到「合流期」。合并成本不是零，只是变得可控。

**实测证据（2 个批次 × 2 个仓的对照）**：

| 批次 | 文件切分 | 结果 |
|---|---|---|
| B 档（枚举收敛） | 业务层 6 文件，与 A 档不相交 | **零冲突**，`git apply` 一次通过 |
| A 档 · 仓1 | 与 B 档文件集完全不相交 | **零冲突** |
| A 档 · 仓2 | 与 B 档有 2 个同文件（双方都要改同处） | **2 处冲突**，须人工/三方合并 |

⇒ 同一套流程、同一批 agent，**冲突有无完全由「文件能否切开」决定**，与是否用 worktree 无关。

> 附带收益（用户实测体感）：worktree 让每个批次的改动**物理上可分辨**（目录即批次），审阅/监控比混在一个工作区里直观。这是选它的正当理由之一——但它是「可观测性收益」，不是「免冲突」收益。

## 二、原理：worktree 是**登记制**，不是一个目录

一次 `git worktree add` 产生**三件互相绑定**的东西：

```
① 登记项      <repo>/.git/worktrees/<名>/      ← 元数据（含指向的 commit、分支）
② 工作树目录  <path>/                          ← 真实文件树（可读可写）
③ 分支        refs/heads/<分支>                ← 该工作树 checkout 的分支（同名分支不能被两个工作树同时 checkout）
```

**推论（决定了清理怎么做）**：

- `git worktree remove <path>` → 同时销 ①②，**目录真的消失**；工作树**脏**时会被拒绝，需 `--force`（会丢弃未提交改动 ⇒ 见 §三-D 前置核验）。
- `git worktree prune` → **只清失效登记**（目录被手工删掉留下的孤儿登记），**不动活跃工作树**。
- **普通目录不受管**：如果一个目录长得像工作树但没有 `① 登记`（`.git` 是个文件、内容为 `gitdir: ...`），那它是**裸副本/symlink 目录/历史遗留**——`remove`/`prune` **都碰不到它**，必须单独判定后处理。
- 分叉边界：`<path>/.git` 是**文件**（一行 `gitdir: <repo>/.git/worktrees/<名>`）= 工作树；是**目录** = 独立仓库（嵌套子仓常见）；**不存在** = 裸副本。

## 三、SOP 四段

### A. 新建

```bash
# 0) 先定基线并核验（必做，最易踩）
git -C <repo> status --short                 # 工作区必须干净，否则基线里混入别人的未提交改动
git -C <repo> rev-list --left-right --count origin/<基线>...HEAD   # 左=落后 右=领先
# 1) 建（每个「批次 × 仓库」一个，别复用）
git -C <repo> worktree add <WORKTREE_ROOT>/<批次名> -b <前缀>-<主题> <基线>
# 2) 核验登记
git -C <repo> worktree list
```

**约定（必须遵守，别自创路径）**：

- **WORKTREE_ROOT 用仓库既定的忽略目录**——先查 `.gitignore` 里有没有现成的（本仓 `内部代码仓/.gitignore` 已有 `.worktrees/`）。**先读约定再建目录**；建到约定外的地方 = 制造噪音 + 事后找不到。
- 目录名 = **批次/主题**（如 `rock-a` / `rock-b`），让人一眼看出「哪个批次、哪个仓」。
- 分支名 = 批次主题（如 `dev-<需求>-observability`）。
- **嵌套子仓是常态**：外层仓对子仓目录常常**零追踪**（`git ls-files <子仓>` = 0），此时只能**进子仓建工作树**，外层 worktree 概念不适用。先判定再动手。

### B. 驱动（让 agent 在指定目录干活）

提示词里必须**显式给**这五项，缺一项就会踩：

1. **绝对路径**：本次要改的**所有** worktree 目录（多仓就逐个列）；
2. **禁止越界**：明确「**只改这些目录**，绝对不要碰主工作区 `<path>`」——主工作区另有并行批次；
3. **真相源**：Spec / 事实源文档的**绝对路径**（尤其工作树在别的目录时，agent 找不到项目内的相对引用）；
4. **构建入口**：把构建脚本写成**绝对路径**（工作树里通常没有 `.Codex/scripts/`），并说明在哪个目录下执行；
5. **完成判据**：把验证命令和期望输出**抄进提示词**（如「这三条 grep 必须为 0」「`git diff --stat -- src/test` 必须为空」）——否则 agent 会用「我觉得好了」交差。

### C. 合流

```bash
# 1) 生成补丁（-N 让新增文件也进 diff；只 diff 不带 commit，适配「AI 不提交」口径）
git -C <wt> add -A -N && git -C <wt> diff HEAD > /tmp/<批次>.patch
# 2) 逐个 check 再 apply
git -C <main> apply --check /tmp/<批次>.patch && git -C <main> apply /tmp/<批次>.patch
# 3) 重叠文件：按文件提取补丁 + 带 fuzz 的 patch 工具
git -C <wt> diff HEAD -- <重叠文件> > /tmp/overlap.patch
cd <main> && patch -p1 --forward --fuzz=5 < /tmp/overlap.patch
```

**顺序**：先合「等价重构/低风险」批次，再合「功能新增」批次（前者给后者一个干净基座）。

### D. 合流后核验（**这一步不能省，见 §五-1**）

```bash
# 内容核验：重叠文件里两批特征是否共存（不是看命令返回码！）
grep -c '<第一批的特征串>' <重叠文件>
grep -c '<第二批的特征串>' <重叠文件>
# 计数核验：批次自带的机械判据（grep 归零 / 断言未改）
# 门禁核验：跑全量测试
```

**移除工作树前的前置核验**（工作树里是未提交改动，`--force` 会丢）：

```bash
# 判据是「子集关系」而非「逐字节相等」——有合流时，主工作区 = 各批次并集
# 对每个工作树：把它 vs 主工作区的差异打印出来，确认差异**恰好是另一批次的改动**
diff <wt>/<file> <main>/<file>
# 通过 → 内容已被主工作区包含 → 可 remove --force；不通过 → 禁止移除
```

### E. 清理（三种情况分开处理）

| 目标 | 判定 | 动作 |
|---|---|---|
| 活跃工作树（有登记） | `.git` 是文件 + `worktree list` 里有 | 核验后 `git worktree remove [--force] <path>` |
| 失效登记（目录已不在） | `worktree list` 有条目但路径不存在 | `git worktree prune` |
| **裸目录/遗留副本**（无登记） | `.git` 不存在 | **人工判定**内容归属 + 是否含独有改动 → 归档或 `mv` 到 /tmp（**不 `rm`**） |

**清理策略二选一，按需**：

- **选择性清理**：批次合流并核验通过后，逐个 `remove`，保留其他批次。适合多批次滚动推进。
- **全量清理**：全部合流 + 全量测试绿后，一次清掉所有工作树 + `prune` + 删批次分支（**注意**：若「AI 不提交」，批次分支零提交、与基线同 SHA，删它不丢任何东西，但要先确认这一点）。
- 两种策略都**必须先做 §三-D 前置核验**。清理完顺手清掉构建产生的 `.orig` / `.rej`（`mv` 备份，不 `rm`）。

## 四、提示词骨架（直接抄改）

```
你是 <角色>。任务：<一句话目标>。

【工作目录（git worktree，已隔离，分支 <分支名>）】
- <仓 A>：<绝对路径>
- <仓 B>：<绝对路径>
⚠️ 只改这些目录里的文件。绝对不要碰主工作区 <绝对路径>（另有并行批次在改）。

【真相源（先完整读再动手；Spec is Truth）】
1. <Spec 绝对路径>
2. <事实源文档绝对路径>

【已冻结的决策（人审通过，不得自行更改）】
<逐条列出 D1/D2/...，含为什么这么定>

【硬约束】
1. <追加式 / 等价重构不许改测试断言 / 不许 commit / 不许引新依赖 ...>
2. 构建一律 `bash <脚本绝对路径> <参数>`，在工作树目录下执行。
3. Java/语言版本、注释语言、命名风格。

【要做的事】<按文件:行给出的改动清单>

【完成判据（逐条抄成可执行命令）】
<grep 计数 / 断言未改 / 测试全绿 / 新增文件存在>

【交付（回报格式）】
改动清单（文件:行）+ 验证证据（实际命令输出）+ 未决项。
发现 Spec 与代码事实不符 ⇒ 停下报告，不要自行改设计。
```

**关键**：「停下报告，不要自行改设计」这一句必须写——否则 agent 会**自己改设计来绕过 Spec 与代码的矛盾**，你就失去了发现 Spec 错误的机会。（本次实测：agent 老实停下来报了 3 处 Spec 计数错误 + 1 处设计矛盾，全部成立。）

## 五、已知坑（都是实测踩过的）

| # | 坑 | 现象 | 对策 |
|---|---|---|---|
| 1 | **`git apply --3way` 静默失败** | 打 `does not match index` → `Falling back to direct application`，然后**什么都没落盘**，**退出码不报错** | 不要只看返回码。合流后**逐文件核内容特征**；或跳过 `--3way`，直接用 `patch -p1 --fuzz=N` 逐文件合并 |
| 2 | 与 §五-1 同源 | 工作区已有未提交改动、而 index 仍指基线时，`--3way` 会整批失败 | 同上；该场景下 `apply --check` 先行，重叠文件单独处理 |
| 3 | **同目录并发写同一文件会互相覆盖** | 两个执行体在同一工作目录用文件编辑器改同一文件 → 后写覆盖前写 | 这正是要开 worktree 的**真实理由**；文件切得开时按文件分工即可避免 |
| 4 | 补丁工具留下 `.orig` / `.rej` | `patch` 生成备份文件，污染工作区 | 清掉：`mv` 到备份目录（**不 `rm`**，红线） |
| 5 | **嵌套子仓的 worktree 隔离不适用** | 外层仓 worktree 不含子仓工作树（子仓是独立 git 仓，外层对它零追踪） | 只能**进子仓**建工作树；先 `git ls-files <子仓> | wc -l` 判定 |
| 6 | 自创工作树根目录 | 建到约定外，事后找不到、父仓 status 出噪音、与既有实践不一致 | **先读 `.gitignore` 的约定**再建 |
| 7 | **等价重构被偷偷改行为** | agent 为了「让测试过」去改测试断言 | 完成判据写死「`git diff --stat -- src/test` 必须为空」；要改断言就是改了行为 ⇒ 停工复查 |
| 8 | 只看 agent 自述就收工 | 「测试全绿」是自述，未复跑 | **主线程独立复跑关键验证**（至少一处：测试 / grep 计数 / 内容核验） |
| 9 | 合流后忘记同步下游文档 | 新关键字/新字段产出后，排障速查文档没登记 ⇒ 白做 | 合流清单里加一项「下游文档登记」（日志关键字表 / 术语表 / 台账） |

## 六、与 specs-engine / sub-specs 的机制衔接

**继承**：一个需求拆多个 sub-spec 时，**冲突以主 Spec 为准**，sub-spec 继承主 Spec 的架构/接口/执行点约定，只在自身范围内派生。worktree 的粒度应与 **sub-spec 粒度对齐**（一个 sub-spec 一个批次/一个工作树），这样「目录名 = 批次 = sub-spec」三者一一对应，可观测性最好。

**统一控制**：共享的东西（新增枚举、常量表、日志关键字、契约）**收敛到主 Spec 或项目级资产**，sub-spec 只引用不重定义。跨仓重复定义（两个独立仓各持一份）必须**在两侧类注释写明同步义务**，并配**机器校验单测**（断言两处集合相等）——没有公共依赖模块时，这是唯一能防漂移的手段。

**回流**：执行中发现的 Spec 错误/设计缺陷，**按 Reverse Sync 先改文档再改代码**（分析 → 补需求/AC → 补验证用例 → 最后改代码），并把结论**回流到**：① Spec 的变更日志 ② 事实源盘点文档 ③ 下游文档（速查表/台账）④ 若推翻了既有规则/harness 判断 ⇒ **反哺规则本身**（本次即推翻了「不用 worktree」那条旧规则）。

**AC 要能机械验证**：sub-spec 的 AC 写成可执行命令（grep 计数、断言未改、字段集合相等），worktree 并行时才能让每个执行体**自证**，主线程只需**抽验**而非全验。物理上限之外，测试留给机器，人只看关键路径与门禁点。

## 七、工具适配层（换成别的 CLI 也照用）

第 1~6 节是纯 git + 工程判断，**任何工具都能执行**。唯一需要按工具替换的是「怎么并行起执行体 + 怎么在它们之间传信息」。适配时回答三栏：

| 能力 | 要回答的问题 | Codex 的答案（示例，非唯一） |
|---|---|---|
| **并行执行体** | 一次能起几个独立执行体？ | Agent 工具起 subagent（可并发一条消息多个） |
| **上下文隔离** | 执行体之间共享上下文吗？ | 独立上下文；需 `fork` 才继承主线程上下文 |
| **目录隔离** | 能指定执行体在哪个目录干活吗？ | 提示词给绝对路径；有 `isolation: worktree` 但**仅对外层仓有效**（嵌套子仓不适用，见 §五-5） |
| **互发消息** | 能中途互通吗？ | 有消息工具；没有的工具则**改用文件传递**（把中间结论落盘，靠 Spec/事实源文档当信道） |
| **权限边界** | 执行体被拒的操作，能不能让它代做？ | **绝对不能**——那是权限洗白，必须回到人 |

**换工具时的最小改动**：§三-B 提示词骨架五项不变（都是绝对路径 + 命令，工具无关）；只把「起执行体」和「传消息」两句换成目标工具的写法。**没有消息工具的 CLI，就用「Spec + 落盘事实源」当信道**——这也是本套方法本来就要求的（真相源落盘优先）。

## 八、项目适配：某零售重构项目（FS）

- **工作树根目录**：`~/projects/内部代码仓/.worktrees/`（**`.gitignore` 已含 `.worktrees/`，这是既定约定，勿自创**；父仓对它的噪音为零）。
- **嵌套子仓**：`内部代码仓` 下的各子仓（模块级目录）各自是**独立 git 仓**（外层零追踪）⇒ 必须**进子仓**建工作树。
- **构建**：一律 `bash ~/projects/内部代码仓/.Codex/scripts/mvn-fs.sh <参数>`（绝对路径；自动 JDK8 + 内部仓库 settings）。子仓工作树里没有 `.Codex/scripts/`，**必须用绝对路径**。
- **提交口径**：本项目约定 **AI 不 commit / 不 push、也不过问是否提交**，产出只落盘为工作区改动 ⇒ 合流走 §三-C 的 `diff` + `apply` 路线（不走分支合并）。
- **既有实践参照**：`.worktrees/` 曾出现过 `fs1908`（132 个 symlink 视图目录，0 实体文件）、`fs1911`（某服务的老副本 + 编译产物）——**都不是登记制 worktree**（无 `.git`），属遗留裸目录，`prune` 管不到，须人工判定。

## 九、自检清单（开 worktree 前 / 合流前 / 清理前）

```
开之前：
□ §一 三问过了吗？（能文件级切开 → 就别开）
□ 基线干净且已 fetch？（git status + rev-list --left-right）
□ 工作树根目录用的是 .gitignore 里的既定约定？
□ 批次粒度 = sub-spec 粒度？
□ 提示词五项齐全（绝对路径/禁越界/真相源/构建入口/完成判据）？

合流前：
□ 重叠文件清单算准了吗（含"注释类改动"这种易漏的重叠）？
□ 合流顺序：低风险在先？
□ 合流后逐文件核内容特征（不看返回码）+ 跑全量测试？

清理前：
□ 逐工作树做过「子集关系」核验（差异恰好是对方批次的改动）？
□ .orig/.rej 已 mv 备份（不 rm）？
□ 遗留裸目录单独出了判定清单（归属/是否含独有改动/可否弃）？
```
