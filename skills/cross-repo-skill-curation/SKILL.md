# 跨仓技能策展蒸馏（cross-repo-skill-curation）

分析另一个仓的 `.claude/` 体系，把真正可迁移的方法论蒸馏进共享技能池，把不该带走的（项目专属、公司侧敏感、官方样例、已有重复）明确挡在门外。**先策展后落地，人审不可跳过。** 产出是"用自己的话重写的通用方法论"，不是源目录的拷贝。

## 五条铁律（先记这个再看流程，v1.2 并入自 cross-agent-skill-distillation）

1. **源只读**：被蒸馏的仓（尤其公司侧）全程只读，任何写操作路径不得指向源仓；交付核对源目录 mtime 未变（Step 7 / Verification 7）。
2. **不整拷**：绝不整目录 copy；落盘内容必过分级→去重→脱敏→重写四道工序（Step 1/2/6）。
3. **增强优先于新建**：重叠时原地增强既有技能或其 `reference.md` + version bump，不新建近重复——双副本腐烂是实锤坑（Step 2）；**双副本收敛前必先 `diff -rq` 判同异，异内容停手重定保留侧，禁盲合防回退（Step 2a）**。
4. **镜像必 diff**：双池同源落盘后 `diff -q` 验证字节相同，一池更新另一池必须同步（Step 7）。
5. **完成认落盘凭证**：`ls -la` + grep 标记 + 冒烟实测 + 留痕行为准，模型自述不作数（Verification 全节）。

## 适用 / 不适用

- **适用**：boss 有多个隔离工作区且各有成熟 `.claude` 体系；说"看看 X 仓有什么值得蒸/搬过来/蒸馏那个项目"。
- **不适用**：治理**当前工作区自身**配置冗余（→ `harness-governance`：KEEP/SIMPLIFY/MOVE/DELETE/CONFLICT 标尺）；从零创作新技能（→ `create-skill`）。本 skill 管"从别人的仓里挑"，那个管"给自己的仓做减法"。
- 目标仓若含公司/客户敏感内容，全程只读，任何其正文/路径/命名 **不得**进入全局池或另一工作区会话。

## 三池模型（去重比对基准）

| 池 | 路径 | 污染风险 |
|---|---|---|
| 全局·千问办公 | `~/.qwenworkcn/skills/` | 注入 boss **所有**会话（含公司侧）→ 只收工作区无关方法论 |
| 全局·Claude | `${SKILLS_DIR}/skills/` | 同上；若需双池同源，落盘后 `diff -q` 验证字节相同 |
| 工作区 | `<项目>/.agents/skills/` 或 `.claude/skills/` | 最安全默认落点；带范围守卫（读根 AGENTS.md 含指定关键词才执行） |

## Steps

### 0. 只读侦察（不动任何文件）

- 清点目标仓：`.claude/skills/*`、`.claude/agents/*`、`.claude/hooks/*`、`CLAUDE.md`、`settings.json`（+ 项目侧 `AGENTS.md`/rules 若有）。
- 每项记录：名称、一句话机制、规模、是否引用私有路径/公司名/内部系统。
- **修正口头假设**：用户说"那仓有很多好技能"≠事实；以磁盘清点为准，完成判定查落盘清单不查模型自述。

### 1. 四分类分级（逐资产打标签）

| 标签 | 判据 | 处置 |
|---|---|---|
| GENERIC-KEEP | 方法论工作区无关（流程/纪律/审查框架），去项目化后可复用 | 进 Step 3 比去重 |
| SKIP-项目·公司专属 | 含公司名/内部系统/私有路径/业务口径，或脱敏后失去意义 | 不搬，报告中列明原因 |
| SKIP-官方样例 | Anthropic/工具方自带模板示例（example、starter 类） | 不搬（无增量价值） |
| DUPLICATE | 现有三池已有同机制 | 转 Step 2 判"增强 or 放弃"，**禁止双份新造** |

判据全表与边界案例见 `reference.md` §一。

### 2. 三池去重比对

#### 2a. 双副本收敛 diff-guard（硬闸门，v1.3 新增）

POOL_LEDGER / 台账标 🔴「双副本实体×2」**不等于**可自动收敛。实测基线：23 项双副本告警里仅 3 项同内容可合并、20 项已分叉（典型：dingtalk-* 系列 qwenwork 侧比 agents 侧新 ~9 天）。逐项按下列顺序执行，禁跳过：

1. `diff -rq 池A/<name>/ 池B/<name>/` 判同异。
2. **同内容**：允许收敛——`mv` 非保留侧到回收站 + `ln -s` 保留侧建软链，落地后 `ls -la` 认软链指向。
3. **异内容**：**停手**，先按 mtime / version / CHANGELOG 判**新旧与活跃度**重定保留侧（**不能默认 agents 为实体、qwenwork 为软链**——分叉侧往往是更新侧），把重定后的保留侧决策写进策展报告交 boss 拍板。
4. **禁盲合**：不做"合并两侧取交集/并集"的自动 merge——那会把新侧的内容回退成旧侧，回退事故比双副本腐烂更严重。

#### 2b. 新候选去重比对

对每个 GENERIC-KEEP 候选，在现有池中 grep 关键机制词（不只看名字——同名不同物、异名同物都要抓）：

- 完全覆盖 → 放弃，报告注明"已有 XX 覆盖"。
- 部分覆盖 → **增强现有**（往既有文件补小节 + version bump），不新造平行技能。实例基准：ctf 仓"何时不并行"裁决矩阵未新造 skill，而是增强进 `specs-engine/references/orchestration.md` §三；对抗审查三点并入 `spec-driven-adversarial-workflow` v1.1→1.2.0。
- 无覆盖 → 进 top-N。

### 3. top-N 深度提炼（默认 ≤5，宁缺毋滥）

每个候选三段式：

1. **核心机制**：它凭什么有效（不是"它是什么"，是"解决什么失败模式"）；
2. **相比现有池新增什么**：一句增量声明，写不出增量的降级为 SKIP；
3. **建议落点**：哪个池 + 全局 or 工作区 + 理由（含污染风险权衡）。

### 4. 出策展报告，停在人审

- 报告含：全量分类表（每资产一行+理由）、top-N 三段式、hooks/守卫类单列、明确"未落地任何文件"。
- **boss 拍板前零落地**。这是硬闸门——"分析了但没乱装"本身就是交付的一部分。

### 5. hooks / 红线守卫类单独评估（不进默认蒸馏）

- 先查**目标工具是否有对应机制**：如 Claude Code PreToolUse hook 只对其宿主 agent 生效；千问办公无用户可注册 hook 层（实测结论，见 `reference.md` §三）——此类守卫只落对应 agent 侧并在 README 写明注册方式，**不擅自改 settings.json/config.yaml**。
- 落地前实测拦截行为：正/反例各跑（含大小写绕过，ctf 案例：大写 `RM -RF` 曾漏拦、补正则后拦截正确）。
- fail-open/fail-closed 策略与红线兜底层（规则层 vs 机械层）写进 README。

### 6. 脱敏剥离（落地内容必过三查）

蒸馏落盘的每一段，逐条过以下判据与检查：

- **换项目判据**：「换一个完全不同的项目，这句话还有意义吗？」没有 → 剥掉或泛化。
- 剥离三类内容：业务专属命令与环境名（构建命令、内部服务前缀、专用运维路径）；真实路径/主机名/账号/内部 URL；公司侧专有名词与可反推个人信息。
- **用自己的话重写**：只保留可跨工作区复用的步骤、判定表、闸门、坑位，标题与措辞不留源项目影子；绝不整目录 copy。
- 机器验证：落盘文件 `grep -c "<业务专属关键词>"` 应为 0 命中。

### 7. 拍板后落地 + 验证留痕

- 蒸出的技能 frontmatter 注明来源仓 + 日期（如"机制源自 ctf 仓 .claude/skills/XX，2026-09-16 策展"），来源仓正文**不复制**、只蒸方法论。
- 双池同源时：落 `${SKILLS_DIR}/skills/<name>/` 后镜像到 `~/.qwenworkcn/skills/<name>/`（或反向），`diff -q 池A/SKILL.md 池B/SKILL.md` 验证字节相同；一池有更新另一池必须同步。
- 增强现有技能时：version bump + 新小节可 grep 验证。
- 清理复核期测试产物（如 hook 实拦测试触发的 `.stats.log`，含**核验者自己**跑测试二次生成的），保持交付纯净。
- 证明源仓只读：交付前核对目标仓 mtime 未变。
- 若目标工作区有留痕惯例（CHANGELOG/产出索引/skill 台账），优先用其自带的并发保护留痕工具回写（避免手拼追加引发并行冲突）；无则至少在本机记录日期与来源。

## 红线与坑位

- **不擅污全局**：含特定项目名/代号/业务口径的专属技能不放全局池（会渗入其他工作区含公司侧会话）；工作区无关方法论才进全局。
- **官方样例不搬**：example/starter 类无增量。
- **DUPLICATE 不双份**：平行副本腐烂是高频事故；能增强不新造。
- **双副本 ≠ 可自动收敛**：POOL_LEDGER 告警只是"存在双副本"信号，不是"内容相同"结论；收敛前必过 Step 2a 的 diff-guard，异内容停手重定保留侧（不能默认 agents 为实体），禁盲合防回退。
- **完成判定查凭证**：以 `ls`/`diff`/`grep`/版本号文件为据，不认"我已经装好了"。
- **公司侧隔离**：策展全程读目标仓可以，但目标仓的私有内容不得回流进其他工作区会话或公网。

## Verification

报告阶段：

1. 报告发出时：确认零文件变更（目标仓与三池 mtime 未动）。

落地阶段（交付前逐项打勾）：

2. 全量分类表已产出，每候选项有类别判定与理由。
3. DUPLICATE 项确认走了增强路径（diff 现有文件可见增量 + version bump），未新建近重复。
3b. 双副本收敛项（Step 2a）：`diff -rq` 结论已记录（同/异）；同内容项软链已建 + `ls -la` 验证指向；异内容项已停手、保留侧重定理由（mtime/version/活跃度）写进报告并经 boss 拍板；无"盲合"痕迹（未出现两侧内容自动 merge）。
4. 新/改文件双池 `diff -q` 同源；单池存在的注明理由。
5. 业务专属关键词 grep = 0 命中；来源标注在位。
6. hook/守卫类：正例反例 + 大小写变体实测全过；测试残留（含核验者自己触发的日志）已清。
7. 目标仓 mtime 未变（只读证明）；工作区留痕已回写（认 CHANGELOG 落盘行，不认模型自述）。

汇报口径：分类表 + 每项"落了什么/为什么没落什么"，让 boss 不必翻历史。
