# 外网放通清单（egress-allowlist）

## 你要解决的事

用户要给一个受限环境（企业内网 / 云桌面 / 隔离区）做**外网访问白名单**，交给对方的安全或网络团队去放通。
常见原话：「这些服务要访问哪些域名」「帮我列个放通清单」。

**你要把他从「知道要放通什么」带到「一份对方能照着配、且配完真能用」的清单。**

---

## 这个技能为什么存在

### 解决什么问题

**放通清单最大的风险不是列多了，是漏了** —— 漏一个域名的表现通常是「**有时能行、有时不行**」，最难排查。

**而最容易漏的，是「实际下载域名」**：

| 服务 | 主域名（大家都记得） | **实际下载域名（容易漏）** | 漏了的后果 |
|------|-------------------|------------------------|-----------|
| **容器镜像** | `registry-1.docker.io` | `auth.docker.io`（换 token）+ **两个 CDN**（`production.cloudflare.docker.com` / `production.cloudfront.docker.com`） | manifest 查得到，**镜像层下载卡死** |
| **VS Code 扩展** | `marketplace.visualstudio.com` | **`*.gallerycdn.vsassets.io`**（扩展本体）+ `*.gallery.vsassets.io`（资源） | **能搜到扩展、装不上** |
| **npm** | `registry.npmjs.org` | （同域，无独立 CDN） | — |
| **Maven** | `repo.maven.apache.org` | `repo1.maven.org`（别名） | 个别项目 pom 显式声明别名时失败 |

> **规律**：**元数据走一个域名，文件走另一个** —— 这是 CDN 时代的常见设计。
> **Docker 还是双 CDN 分发** —— 只放一个会出现**随机失败**。

### 不解决什么（边界）

- ❌ **不替对方决定放通方式** —— 但要**讲清「域名 vs 网段」的利弊**（见下）
- ❌ **不保证放通后一定能通** —— 我们只能证明域名有效，**实际连通性要对方环境实测**
- ❌ **不猜域名** —— 查不到就说查不到

### 决策依据

| 决策 | 否决了什么 | 为什么 |
|------|-----------|--------|
| **按域名列，不按网段列** | 给 IP 段 | 服务多在公共 CDN 上，按网段要放通**整个 CDN 段**（上面托管海量其他站点，等于没设防），且 **CDN 的 IP 会变** |
| **必查「下载域名」而非只列主域名** | 只列官网/主域 | 主域名常只负责元数据，**文件走 CDN** —— 不查就会「能查不能下」 |
| **不硬顶对方的标准做法** | 直接说「你们该用域名」 | 给依据 + 留余地：**「若策略只能按网段，请告知，我们另行评估最小范围与风险」** |

---

## 三条铁律

1. **查「下载域名」，不只列主域名** —— 每个服务都问一句：**元数据和文件，是不是同一个域名？**
2. **实测，别只查文档** —— 至少对主域名做一次可达性验证；**官方 allowlist 可能滞后**（Docker 官方就只列了一个 CDN，实际有两个）
3. **清单里写清「待确认」** —— 对方环境能否连通、是否支持通配符，**标出来，不替对方断言**

## 流程

### 第 1 步：定技术栈
跑什么语言/构建工具/编辑器 → 决定要覆盖哪些制品源。

### 第 2 步：列主域名
从各服务的官方文档取 canonical 域名（**别用博客里的**）。

### 第 3 步：⭐ 查真实下载域名（**本技能的核心价值**）

对**每一个**服务，回答：**查询走哪？下载走哪？**

- 查官方 allowlist / firewall 文档（很多服务有专门的）
- 查包管理器实际请求的域名（如看 tarball URL、看 `docker pull` 的报错）
- **交叉验证**：官方文档可能滞后，社区实测能补（如 Docker 的双 CDN）

### 第 4 步：实测可达性
至少对主域名跑一次请求，**把 HTTP 状态附在清单里**。

> ⚠️ **注意**：**你本机的可达性 ≠ 对方环境的可达性**。本机不通可能是本地网络问题；本机能通也不能证明对方能通。

### 第 5 步：出清单

**必含要素**：
| 要素 | 为什么 |
|------|--------|
| **方向**（出站/入站） | 对方按方向配策略 |
| **端口** | 通常 443 |
| **每个域名的作用** | 讲不清作用的域名，对方没法审 |
| **「待确认」清单** | 通配符支持？SSL 拦截？——**不替对方断言** |

**加一节「放通方式说明」**：讲 `域名 vs 网段` 的利弊 + 给对方留退路。
