# 会议归档（meeting-archive）

## 你要解决的事

用户刚开完会，手上有的是这几种之一或几种：

1. **一个飞书文档链接** —— 妙记 / 云文档里的会议纪要（**能给链接直读，但需公司先开通凭证**）
2. **一个豆包文档链接** —— 智能纪要（含纪要 / 原始记录 / 音频，**无 API，需人工导出**）
3. **本地文件** —— 微信里收到的 `.docx`、Teams 下载的文档、已导出的 Markdown

他的诉求就一句话：

> **"把这次会归档一下。"**

**你要把他从「文件散在微信下载目录 / 桌面」带到「规范归档进 `meeting/`，同事打开就能看、能搜、能回溯」。**

---

## 用 IPO 理解这件事

```
Input（输入）                Process（加工）                Output（输出）
───────────────────         ──────────────────            ──────────────────────
A 飞书文档链接          →   ① 查重（md5）             →    meeting/{日期}-{主题}/
   （CLI 直读，需凭证）        ② 规范化命名                  ├── 逐字稿_{日期}.md  ★最高信息源
                           ③ docx → Markdown             ├── 纪要_{日期}.md
B 豆包文档链接          →   ④ 提炼要点 → 写文件头         └── 附件/（原件 + 音频）
   （人工导出 Markdown）       ⑤ 写文件头 + 来源               ↓
                                                        更新 meeting/README.md 清单
C 本地文件（微信/Teams）→
```

**三段各归各**：输入「拿到材料」→ 加工「变成规范件」→ 输出「归档 + 可检索」。**别跳步，别合并**。

> ⚠️ **三条通道的可行性差很多** —— 详见下方「第 1 步」，**别对用户空头承诺能"给个链接就自动拉"**。

## ★ 逐字稿优先原则（本技能最重要的一条）

> **逐字稿是唯一能回溯「当时原话是什么」的东西。**

| 层级 | 文件 | 地位 |
|:--:|------|------|
| **1（最高）** | **逐字稿 / 原始记录** | **信息源头**。纪要、提炼、待办都从它出发 |
| 2 | 纪要（提炼版） | 原文的**加工品**，方便快速阅读 |
| 3 | 要点提炼（文件头） | 加工品的**索引** |

**三条推论**：

1. **逐字稿永远保留原文** —— 不删减、不改写、不"顺手润色"
2. **纪要必须能回溯到逐字稿** —— 写"会上决定 X"时，能从逐字稿里找到对应原话
3. **冲突以逐字稿为准** —— 纪要与逐字稿不一致时，**错的是纪要**

> 💡 **豆包的「导出原始记录」就是逐字稿** —— 优先导它，别只导纪要。

## 这个技能为什么存在

### 解决什么问题

**手工归档有三个反复出现的毛病**（不是偶发，是每次都会犯）：

| 毛病 | 实际后果 |
|------|---------|
| **文件名乱** | 带空格、全角冒号、`(1)` 后缀 —— `智能纪要：项目背景与工作安排讨论 2026年9月16日.md` |
| **同一份内容存两遍** | 「智能纪要」与「智能纪要-逐字稿」两份 27.0K 文件，**md5 完全相同** |
| **docx 直接丢进仓** | GitLab **不能在线预览**、`git diff` 读不了、全文搜索搜不到 |

### 不解决什么（边界）

- ❌ **不生成纪要** —— 那是豆包干的活，本技能只做**归档**
- ❌ **不改写内容** —— 正文一个字不动；提炼只放在**文件头**
- ❌ **不从纪要里"识别待办"** —— 见下方「为什么不做待办识别」
- ❌ **不判断会议内容对不对** —— 那是人的事
- ❌ **不管非会议材料** —— 文档翻译走 `doc-translate`，周报走 `report/`

### 为什么不做「待办识别」

**用户的原始想法是从纪要里自动提取待办。这件事被有意排除。**

| 理由 | 说明 |
|------|------|
| **违反单一职责** | 归档技能管「**把材料放对地方**」；待办提取是「**从材料里读出行动项**」—— 两件事，两个技能 |
| **来源不同** | 待办应该从**逐字稿**出发（原话最准），从**纪要**出发会二次失真 |
| **正确做法** | 另建一个技能（如 `action-extract`），**消费本技能归档好的逐字稿** —— 归档在前，提取在后 |

> **本技能为那个未来技能做的一件事**：**保证逐字稿完整、规范地进了仓。** 地基打好了，上面盖什么楼都行。

### 决策依据（否决了哪些替代方案）

| 决策 | 否决了什么 | 为什么 |
|------|-----------|--------|
| **docx 原件 + 转 md 都存** | 只存 md / 只存 docx | 只存 md → 排版丢失不可还原；只存 docx → 不能预览不能搜。**两份各有用途** |
| **用子目录而非平铺** | 别的仓的平铺命名法 | 平铺「按文件名排序 = 时间线」很优雅，但**我们仓的约定已定子目录**（见 `AGENTS.md` §三），且一场会常带 3-4 个文件 |
| **借鉴别处的会议清单做法** | 只归档不建索引 | 对方那堆文件还能用，**靠的就是 README 里那张全量表**。文件一多，没清单没人翻 |
| **提炼放文件头，不动正文** | 直接改纪要正文 | 纪要是**原始记录**，改了就失去凭证价值 |

---

## 三条铁律

1. **逐字稿优先** —— 有逐字稿才有"原话"，才有日后回溯的余地（见上方专节）
2. **原件不丢** —— docx 原件、音频永远进 `附件/`。转 md 是**加值**，不是替代
3. **先查重再入库** —— 入库前 `md5` 比对。同一份内容不存两遍（**这个仓已经犯过一次**）

## 标准归档结构

```
meeting/{YYYYMMDD}-{主题}/
├── 逐字稿_{YYYYMMDD}.md      ★ 原始记录（最高信息源，原文不动）
├── 纪要_{YYYYMMDD}.md        ← 提炼版（带要点）
├── 相关方清单_{YYYYMMDD}.md   ← 参会人 + 提及方 + 对接关系（见第 7 步）
└── 附件/                     ← 微信原件（.docx）、音频、截图
```

**命名要求**：

| 项 | 规则 | 反例 |
|----|------|------|
| 目录 | `{YYYYMMDD}-{主题}`，主题用简短 slug | `20260916-kickoff` ✅ |
| 文件 | `逐字稿_{YYYYMMDD}.md` / `纪要_{YYYYMMDD}.md` | `智能纪要：…(1).md` ❌ |
| 禁止 | 空格、全角冒号、`(1)` 这类下载后缀 | — |

## 流程

### Input 阶段

#### 第 0 步：问清三件事

```
1. 哪天的会？      → 目录名里的日期
2. 什么主题？      → 目录名（如 "项目启动会" → kickoff）
3. 材料在哪？      → 豆包链接？微信里的 docx？还是都有？
```

> 用户常只丢一个链接。**能从内容读出日期和主题就别问** ——
> 做完在报告里说明判断依据即可。

#### 第 1 步：取内容（**四通道，可插拔**）

**先说清现状 —— 这几个平台的自动拉取门槛差很多，别对用户空头承诺。**

| 通道 | 能不能自动拉 | 现状 | 接入条件 |
|------|:--:|------|---------|
| **A 飞书文档链接** | ✅ **可以** | **接口预留，待实测** | `config init --new` **一键建应用** + `auth login` **个人授权一次**（详见下）；⚠️ 是否放行取决于租户管理员策略 |
| **B 豆包文档链接** | ✅ **可以**（**2026-09-28 打通**） | **全自动** —— 首次登录一次，之后零人工 | 跑 `bash scripts/doubao.sh login` **一次**（扫码）；之后 `bash scripts/doubao.sh fetch <URL>` 直接出逐字稿 |
| **C 本地文件**（微信/Teams 下载的 docx、导出的 md） | ✅ 就是文件 | **当前主力** | 无 |
| **D Teams 参会人截图 / 实时字幕**（⭐ **定人唯一可靠来源**） | ✅ 就是图片 | **强烈建议索取** | 让用户截 ①「参与者」面板 ②字幕区 |

##### 通道 B 怎么打通的（**2026-09-28 逆向 + 实测通过**）

**结论先给**：豆包文档的正文由**飞书妙记 API** 提供 —— 页面背后是两个 JSON 接口：

| 接口 | 给什么 |
|------|--------|
| `my.feishu.cn/minutes/doubao/api/subtitles_v2?size=100000` | **paragraphs[]** —— 正文 + 时间戳 + `pid` |
| `my.feishu.cn/minutes/doubao/api/speakers` | **paragraph_to_speaker{}** —— `pid` → 说话人编号 |

**按 `pid` 关联两者 = 完整逐字稿**（`@说话人 N` + `MM:SS` + 正文），与豆包「导出原始记录」等价。

**实测比对**（2026-09-24 两场会）：

| 文档 | 自动抓取 | 人工导出 |
|------|:--:|:--:|
| 内部筹备（中文） | **129 段** / 23,089 字符 | 129 段 / 23,220 字符 |
| 客户沟通（英文） | **115 段** / 56,848 字符 | 115 段 / 56,235 字符 |

**段数完全一致**，差异仅在空行格式。

**怎么用**：

```bash
bash scripts/doubao.sh login                   # ① 一次性：弹出 Chrome，扫码登录
bash scripts/doubao.sh fetch <URL> [输出目录]   # ② 之后每次：直接出逐字稿 + 原始 JSON
```

**六条「别再试一遍」的弯路**（都踩过，记下来省时间）：

| 试过什么 | 结果 |
|---------|------|
| `curl` 直接抓文档页 | HTTP 200，但只拿到 **1.5MB 的 SPA 空壳**，正文由 JS 渲染 |
| **滚动抓 `innerText`** | ❌ 豆包用**虚拟滚动**，只能拿到当前视口那几百字（实测仅 637–842 字符） |
| **点「下载」按钮** | ❌ 浮层是 **canvas 渲染**，DOM 点不到（按钮能命中，菜单出不来） |
| **`ego-browser`** | ❌ **无头浏览器、无可见窗口** → 用户没法扫码（本方案与之无关，当时走错了路） |
| **Playwright 自带 chromium** | ❌ 版本与本机缓存不匹配（要 1229、缓存 1234）→ **改用 `channel: 'chrome'`（系统 Chrome）** |
| 抓 `doubao.com` 域名的接口 | ⚠️ 正文不在那边，在 **`my.feishu.cn`（飞书妙记）** 那边 |

> ⚠️ **首次仍需人工一次**（扫码登录），**之后全自动**。登录态存 `~/.claude/doubao-profile`，脚本自动复用。

##### 通道 D：为什么它比逐字稿还重要

**语音转写不认识人，Teams 认识。**

| Teams 给什么 | 逐字稿给什么 |
|------------|------------|
| 参会人**真实姓名 + 账号**（"张三（组织者）"） | `说话人 3` |
| 实时字幕**带说话人名**（"某平台 - 某同事：……"） | `说话人 6  15:31` |
| 谁在会议室、谁后加入（"已添加到聊天中"） | 无 |

**所以**：拿到逐字稿后，"**谁在说**"这个问题**只能靠通道 D 回答**。用户手上有截图时，**主动要**——一句话的事，能省掉整场会的身份猜测。

##### 通道 A：飞书文档链接（**接口已预留 —— 门槛比想象的低**）

> 飞书妙记 / 云文档里的会议纪要 —— 这类**能给链接直接读**。

**飞书官方 CLI 就是为 AI Agent 设计的**（`larksuite/cli`，MIT 开源，自带 19 个 agent skills）。
**建应用 + 授权只需一次，且不用进开放平台控制台手动建**：

```bash
npm install -g @larksuite/cli     # 官方 CLI

lark-cli config init --new        # ① 一键创建应用（绑定租户的 Personal Agent）
                                  #    会给出验证链接/二维码，用户在飞书里确认
lark-cli auth login --recommend   # ② 个人授权（OAuth Device Flow，点链接确认即可）
                                  #    token 存进系统钥匙串，自动刷新
```

完成后 `lark-doc` / `lark-drive` 相关命令即可**按链接直接读文档** → **直接进 Process 阶段**（后续流程完全复用）。

**需要的飞书权限**：`docx:document:readonly`（新版文档）、`drive:file:readonly`（图片附件）、`wiki:wiki:readonly`（若在知识库）。
权限不够时增量授权：`lark-cli auth login --scope "<缺失的 scope>"`。

**⚠️ 唯一的未知数**（**不要对用户打包票**）：

> 飞书官方 FAQ 说明：CLI 只提供"一键建应用"的能力，**应用的管控仍遵循企业统一管控规则**。
> 即 —— **能不能跑，取决于所在租户的管理员策略**是否允许成员自建应用。

**所以**：遇到用户给飞书链接时，**先试**（`auth status` 看是否已授权）；
被策略拦住了，**退到通道 B 的话术**："飞书这边自建应用被租户策略限制了，麻烦你导出一份 Markdown 给我。"

**Agent 友好特性**：`auth login --no-wait --json` 立即返回验证链接（不阻塞），
后续用 `--device-code <CODE>` 续上 —— 适配不能长时间同步等待的 AI 工作流。

##### 通道 B：豆包文档链接（**当前只能人工导出**）

> 链接形如 `https://www.doubao.com/docx/xxxxxxxx`

**豆包没有公开的文档读取 API** —— 所以只能让用户点导出。

**豆包文档页右上角有「导出」按钮**，三个选项 —— **按优先级要**：

| 优先级 | 导出项 | 落到哪 |
|:--:|--------|--------|
| **1（最高）** | **导出原始记录** | → `逐字稿_{日期}.md` |
| 2 | 导出纪要 | → `纪要_{日期}.md` |
| 3 | 导出音频 | → `附件/`（可选） |

**格式选 Markdown**（另有 Word / PDF，都不便于 diff 和搜索）。

> **话术**：把上表直接发给用户，一次导齐 —— 别让他来回问"要导哪个"。

##### 通道 C：本地文件（**当前主力**）

用户给的本地路径。常见来源：

| 来源 | 典型路径 |
|------|---------|
| **微信**收到的 docx | `~/Library/Containers/com.tencent.xinWeChat/Data/Documents/xwechat_files/<账号>/msg/file/<YYYY-MM>/<文件名>.docx` |
| **Teams** 下载的 docx | `~/Downloads/` |
| 豆包导出的 md | `~/Downloads/` |

**直接取用，别让用户再翻一次。**

### Process 阶段

#### 第 1·5 步：先用「干系人词表」校正（**语音转写必做**）

**语音转写（豆包 / Teams 智能纪要 / 任何 ASR）对人名和术语的识别很差，而且同一个人会被转成好几种写法。**

实测例子（一场会里同一个人出现了 **4 种写法**）：`Deepan` / `Deepak` / `divan` / `Dipen`。
术语同样（`4V CP` / `VP C` / `4V CPU` 指同一个参数）。

**所以：拿到转写稿后，先拿项目词表对一遍，再往下做。**

**去哪找词**（按序，**两类词表都要**）：

| # | 找什么 | 常见命名 | 用来干什么 |
|:--:|--------|---------|-----------|
| 1 | **人名/术语词表** | `glossary-people.md` · `glossary.md` · `术语表*` | **定名** —— 这个人名怎么写、那个误转指的是谁 |
| 2 | **干系人表**（若项目有） | 带 **头衔 / 业务域 / 业务范围 / 上级** 列的清单 | **定职责** —— 只靠人名定不出"他管什么"，职责要靠头衔列 |
| 3 | 都没有 | — | **问用户要一份** —— 别自己猜人名怎么写 |

> ⭐ **经验和人名的价值不同**：词表告诉你"`Deepan` 别写成 `Dipan`"；**干系人表告诉你"Deepan 管 AVD 工单和 host pool 建设"**。
> 后者才是"判断每个人职责"的依据（也是会议分析的准确率来源）。
> **用户手上有这类表时，主动要** —— 一次要到，之后每场会都受益。

**校正完要回填**（这一步最容易被跳过，但**词表越用越准只靠它**）：

| 发现什么 | 回填到哪 |
|---------|---------|
| 新的**误转写法** | 词表「常见误转」列 + 别名索引 |
| 新出现的**人名** | 干系人表加一行（**含头衔与业务范围**） |
| **同一缩写指两人**（真实踩过：`Steven` = 华为云 Li Yibin / 客户 Hu Hao） | 词表里建**歧义警示**，要求"单写缩写时回原文判断" |

**校正什么**：

| 校正对象 | 做法 |
|---------|------|
| **人名** | 按词表「规范名」统一；词表里有「常见误转」列的，**把误转也一并替换** |
| **术语** | AVD / Podman / Info team 这类，转写常错（如 `Abd`→`AVD`、`portman`→`Podman`） |
| **数字/参数** | 转写会自相矛盾（`4V CP / VP C / 4V CPU`）→ **保留原文并在译文里标 `[转写存疑]`**，不替发言人选 |

**两条边界**：

1. **词表里没有的人名，不要猜** —— 保留英文原名，或标 `[人名待核]`
2. **校正的是"定名"，不是"改写原文"** —— 逐字稿的**原文照旧**，校正体现在**译文和后续材料用规范名**

> ⚠️ **为什么值得单列一步**：名字错了，**后面所有材料都跟着错**（往期真实事故：把 `xudongli` 猜成"李旭东"，实为"徐东立"）。



#### 第 1·6 步：识别「谁在说」（**逐字稿的固有缺口，必须补**）

**豆包/Teams 的逐字稿只有 `@说话人 1` `@说话人 2`——没有任何名字。**
**一场会里「谁说了什么」，是会议分析的地基。** 不补这一步，纪要只能写成"会上有人提出…"。

**三源交叉，逐条定人**：

| 源 | 给什么 | 可靠度 |
|----|-------|:--:|
| **① Teams 参会人截图 / 实时字幕**（通道 D） | 真实姓名 + 账号 + 角色标记（"组织者"）；字幕**直接带说话人名** | ✅ 最高 |
| **② 逐字稿自报名** | `"This is 张三 speaking"` / `"我是 李某"` | ✅ 高（自报即为准） |
| **③ 发言内容特征** | 主导议程、点名他人、承诺给资源的人 = **会议组织者**；讲某应用细节的人 = **该应用 SME** | 🟡 推断 |

**产出格式**（写进相关方清单）：

```markdown
| 标签 | 推定身份 | 置信度 | 依据 |
|------|---------|:--:|------|
| 说话人 3 | **张某** | 🟡 | 主导议程 + 截图标注"组织者" |
| 说话人 5 | **李某** | ✅ | 自报 "this is 李某 speaking" |
| 说话人 6 | **王某** | ✅ | 自报 "This is 王某 speaking" |
| 说话人 4 | 客户方管理层（**谁待定**） | 🔴 | 内容像多人被并到一个标签 —— **不可靠** |
```

**三条纪律**：

1. **置信度必须标**（✅ 自报 / 🟡 特征推断 / 🔴 不确定）—— 让人知道哪条能信
2. **不确定的就说"不可靠"，不要硬编一个人名** —— 转写会在多人交替发言时**把多人并进同一个说话人标签**，这时老实标 🔴
3. **客户侧"谁说了什么"要能回溯** —— 纪要里写"客户方要求 X"，最好能指到具体人；指不到就写"客户方（未定人）"

> ⚠️ **为什么不能跳过**：纪要写"客户说迁移后 UI 不变"和写"**客户方负责人**说迁移后 UI 不变"，**分量完全不同**——后者才敢拿去对外。

---

#### 第 2 步：查重（**别跳过**）

```bash
md5 -q <新文件> ; md5 -q <已有文件>
```

**判据**：md5 一致 → **不重复入库**，在报告里说明"已有同内容文件"。
> 名字不同但内容一样，是**下载了两遍**，不是两份材料。

#### 第 3 步：docx → Markdown

```bash
pandoc "原件.docx" -t gfm --wrap=none -o "转换结果.md"
```

- `-t gfm`：GitHub 风格 Markdown（GitLab 直接渲染）
- `--wrap=none`：**不要自动折行**（否则 diff 会碎成一片）

#### 第 4 步：提炼要点 → 文件头

**只从逐字稿提炼**（纪要已是二手）。写三类：

| 类型 | 写什么 | 判据 |
|------|--------|------|
| **决策** | 定了什么、谁定的 | 有明确结论 |
| **待办** | 谁、做什么、什么时候 | 有责任人和时间点 |
| **风险 / 待澄清** | 还没结论、有分歧 | 会上没拍板 |

**铁律**：提炼是**摘录**，不是**改写**。
写"老张说 7/23 前给方案"，**不写**"团队决定推进方案"。

#### 第 4·5 步：翻译（**外语会议必做**）

> **我们多数会议是外语（英文）交流** —— 材料和纪要**都要能看懂**，不是每个人都读得顺原文。

**翻译这一步，用 `doc-translate` 技能，别自己翻。**

> **为什么不写在这里**：翻译有它自己的一套要求（提取、术语、对照格式）——
> 那些**归 `doc-translate` 管**，这里只负责**指出该用它**。**复制过来会漂移。**

**要翻什么、翻成什么**：

| 材料 | 处理方式 |
|------|---------|
| **逐字稿** | **中英对照** —— **原文完整保留 + 译文另起**（逐字稿是原始记录，不能替换） |
| **纪要** | **直接出中文** —— 纪要本就是提炼加工品，不必中英对照 |
| **附件里的外语文档** | 中英对照（走 `doc-translate` 的标准流程） |

**三条要求**（沿用 `doc-translate` 的铁律）：

1. **1:1 完整翻译** —— 不因"安全""简洁"擅自删减
2. **原文一字不改** —— 译文**另起一行**，不替换原文；逐字稿尤其如此
3. **识别不清就标 `[识别不清]`** —— 语音转写常有噪音（同音错字、无意义碎片），**不脑补**

> ⚠️ **人名保留英文原名**，不要自己音译成中文 —— 猜错名字比不翻更糟。

##### 先判断这场会**要不要翻**

| 会议语言 | 逐字稿 | 纪要 | 动作 |
|---------|--------|------|------|
| **中文会**（内部筹备 / 内部对齐） | 中文 | 中文 | **不翻译** —— 只做人名/术语校正 |
| **英文会**（客户例会 / 跨国同步） | 英文 | 中文 | **逐字稿中英对照** + **纪要直接出中文** |
| **中英夹杂** | 混合 | 中文 | 逐段判断，**只有英文段加对照** |

> ⚠️ **别对中文会做"翻译"** —— 那只是把中文抄一遍，纯浪费算力。

##### 逐字稿对照的推荐格式

**英文原文照抄原样**（含原始错拼、大写、空格异常），**中文译文用引用块另起**：

```markdown
@说话人 7  30:27
So these are the models that we have.The maintenance, all Master Table...

> 【译】这些是我们的模块：维护……全部是主表……
```

**为什么用引用块**：一眼分清原文与译文；且**原文段落可被 `grep`/`diff` 逐行比对**（下面就用到了）。

##### ⚠️ 翻完必须跑完整性校验（**这一步不能省**）

**铁律是"原文一字不改"。人手抄 100+ 段，必然有手误。**

```bash
# 原文的每一行，是否都原样出现在产出稿里
while IFS= read -r line; do
  [ -z "$line" ] && continue
  grep -qF "$line" 产出稿.md || echo "❌ 缺失: ${line:0:80}"
done < <(grep -v '^@说话人' 原文.md | grep -v '^# ' | grep -v '^> ')
```

**实测威力**（2026-09-28，115 段英文逐字稿）：这个脚本抓出 **2 处手误**——
都不是漏段，而是**多打了一个逗号、少打了一个空格**（`I mean, the workload` ↔ 原文 `I mean the workload`；`right?Users` ↔ 原文 `right? Users`）。
**肉眼绝对看不出来，但"一字不改"就是一字不改。**

**段数也要对得上**：

```bash
grep -c '^@说话人' 原文.md 产出稿.md    # 两边数字必须相等
grep -c '^> 【译】' 产出稿.md          # 译文条数应等于原文段数
```

> **判据**：**能用一个数字验证的，就别用眼睛看。**

#### 第 5 步：写文件头

```markdown
> 归档时间：{YYYY-MM-DD HH:mm} | 会议日期：{YYYY-MM-DD}
> 来源：{豆包链接 / 微信文件名}
> 原始文件：附件/{文件名}（如适用）
```

### Output 阶段

#### 第 5·8 步：分级落库（**本地全量 → 选择性共享**）

**这一步决定"哪些内容能出工作空间"。做错了要么漏共享，要么把内部话送出去。**

**核心模型**：

```
本地工作空间（全量主库）             会推 git 的共享仓（选择性子集）
      │                                        ▲
   全部材料                         只 copy「可给同事/客户看」的那部分
 （含内部成本、对客户的判断）           ⚠️ 不是 move —— 本地永远留全量
```

**三条铁律**：

| # | 规则 |
|:--:|------|
| 1 | **本地是全量，共享仓是子集** —— **是 copy 出子集，不是 move 走**。本地永远保留完整材料（否则日后想查内部口径就没了源） |
| 2 | **判据**：**「这条信息如果被同事、客户方或项目组看到，我会不会难受？」** 会 → **不进共享仓** |
| 3 | **一场会常有两条线**（内部筹备 + 客户沟通）—— **客户沟通可共享，内部筹备通常不能** |

**典型分级**：

| 内容 | 去向 |
|------|------|
| 客户沟通会纪要 / 逐字稿 / 相关方清单 / 技术方案 | ✅ 可共享 |
| 人天 / 成本口径 / 立项策略 / 报价内部逻辑 | ❌ 只留本地 |
| **对客户的负面判断**（"人家就是不想让我们进来"） | ❌ **只留本地** |
| 范围裁剪策略（尚未告知客户的） | ❌ 只留本地 |
| 同事评价、内部博弈 | ❌ 只留本地 |

> ⚠️ **共享仓若是公司 GitLab / GitHub，管理员与全局搜索都能看到** —— 别把"私有仓"当"没人看得到"。
> ⚠️ **拿不准先问用户**：这场会能不能共享、共享哪些 —— **一次问清，别替他判断**。

---

#### 第 6 步：识别相关方（**有截图/纪要时做**）

**同一个信息源，多一个产出。** 从**参会人列表 + 纪要提及**里识别干系人，出 `相关方清单_{日期}.md`。

| 要识别的 | 从哪来 |
|---------|--------|
| **本次参会人** | 会议截图的「参与者」列表（**截图是这一项的唯一来源**） |
| **纪要提及但未参会** | 纪要正文里出现的团队/人名（如 info team、security team） |
| **关键人物映射** | ⭐ **纪要里的昵称 ↔ 参会人真名**（如 "Jin" = Jeen Gunaseelan） |
| **按事项的对接关系** | 纪要里的分工（谁负责 AVD、谁负责白名单…） |
| **沟通渠道规则** | 纪要里明确的（邮件正式 / 某工具被禁…） |

**清单结构**（模板）：
```markdown
# {会议名} 相关方清单（{日期}）
## 一、本次参会人员（按侧分组：我方 / 客户 / 第三方）
## 二、纪要提及、但未参会
## 三、关键对接关系（按事项）
## 四、沟通渠道规则
## 五、待核实（人名拼写 / 角色边界等）
```

**三条要求**：

1. **必须标"待核实"** —— 人名拼写、角色边界，**拿不准的列出来**，别编
2. **昵称映射是关键产出** —— 纪要常写昵称，参会列表是真名，**对上了后续才看得懂纪要**
3. **截图唯一** —— 参会人只从截图来（纪要通常不列全）；**没有截图就说"参会人待补"**

> ⚠️ **不做推断** —— 截图里没有的人**不往"参会"里写**；纪要没说的职责**不替他编**。
