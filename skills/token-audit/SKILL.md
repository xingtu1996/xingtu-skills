# Token 体检与瘦身（token-audit）

## 你要解决的事

用户感觉「AI 越来越贵 / 越来越慢 / 越用越不听话」，但**说不清钱花在哪**。

典型说法：

> 「感觉 token 花得好快」「上下文总是很满」「我们配置是不是太肥了」
> 「多 agent 一跑就爆」「帮我看看怎么省点」

你要把他从「感觉贵」带到「**知道钱花在哪、哪些能省、哪些别碰**」。

---

## 这个技能为什么存在

- **解决什么问题**：AI 工作区的"常驻配置"（每次会话必注入的系统提示 / 规则 / 技能索引 / 子代理描述）会随时间膨胀。膨胀的代价有两层：① 挤占任务本体的上下文 ② **在 Multi-Agent 场景下要乘 agent 数量**——用户往往只感觉到贵，看不到这层乘数。
- **不解决什么（边界）**：
  - ❌ **不治"机制决定"的东西** —— Claude Code 的加载机制改不了，只能减文件（见第 2 步）
  - ❌ **不压不占常驻的内容** —— 技能正文、模板、specs 历史文件是**按需加载**的，压了白压
  - ❌ **不做语义取舍** —— 「这条规则还要不要」归人；本技能只做**可逆操作**（备份 / 移走 / 指针化）
  - ❌ **不跨工作区** —— 只治当前工作区这一套 harness
- **决策依据（否决了什么）**：
  - **否决"新建一个独立的常驻治理技能"** → 已有通用治理技能（如 `harness-governance`）覆盖流程，本技能只补**Claude Code 特化的领域知识**（机制 / 成本模型 / 安全），不重复流程
  - **否决"直接删冗余文件"** → 一律走**可逆操作**（移入回收站 / 备份），因为文件常被隐式引用
  - **否决"按触发频次自动关技能"** → 低频 ≠ 无用，自动触发 ≠ 显式调用；休眠名单必须人拍板

---

## 三条铁律

1. **先分「机制」和「配置」，再动手** —— 机制决定的（自动加载、渐进披露）改不了，只能减文件；把机制问题当配置"治"是白费力气（见第 2 步）
2. **只移不删，备份先行** —— 任何写入前先备份；拿不准的先沉降（按需加载 / 移到参考层），物理删除是最后手段且需人确认
3. **常驻收益按 agent 数量放大** —— 评估优先级时，**常驻层的每 1 KB 都要乘 N**（N = 典型并行 agent 数）；这才是 Multi-Agent 场景下最该先做的一类优化

---

## 第 0 步：先问清楚（别猜）

**只问一件**：**「你日常怎么用它？」** —— 单选，决定后面的算法

| 用法 | 说明 | 影响 |
|------|------|------|
| **A. 基本单会话** | 一个人对着 AI 干活 | 收益按 1× 算，重点看会话内容 |
| **B. 常派子 Agent** | 会 fan-out 给多个 agent | 收益按 N× 算，**常驻层优先** |
| **C. 都用**（默认） | — | 按 B 的算法给结论，同时标注单会话收益 |

> 其余**一律自己搞定**：`/context` 能拿的、`ls`/`wc` 能量出来的，别问用户。

---

## 第 1 步：量（只读，零写）

**别用眼睛估，用数字。**

### 1.1 拿第一手数据

用户能跑 `/context` 就让他跑（图表最直观）；拿不到就自己测：

```bash
# 常驻文件的体积（按 Claude Code 的加载面分类）
#  ① 各级 CLAUDE.md
#  ② .claude/rules/ 下的全部（会**自动加载**，见第 2 步）
#  ③ 技能数量（只有 description 常驻）
for d in ~/.claude "$PWD/.claude"; do
  [ -d "$d" ] || continue
  echo "== $d =="
  find "$d" -maxdepth 2 -name "CLAUDE.md" -o -path "*/rules/*" -name "*.md" 2>/dev/null \
    | xargs wc -c 2>/dev/null | tail -1
done
echo "技能: $(ls ~/.claude/skills "$PWD/.claude/skills" 2>/dev/null | wc -l)"
```

### 1.2 对三条标尺

| 标尺 | 阈值 | 含义 |
|------|------|------|
| **常驻上下文占比** | **< 有效窗口 5%** | 每次必注入的 token 不该挤占任务本体 |
| **主入口文件行数** | **< 200 行**（>400 开始漏读） | CLAUDE.md 超了就是 kitchen sink |
| **单文件大小** | **< 16 KB** | 单个规则文件超了应拆分或按需加载 |

> **换算参考（实测校准，别用直觉估）**：混合中英文 + 代码的配置文本约 **4.6 字符/token**（即 **1KB ≈ 220 tokens**）。
> ⚠️ **踩过的坑**：曾按"中文 1.5 字符/token"估，把 173KB 算成 **115K tokens**，而 `/context` 实测只有 **37.4k** —— **差 3 倍**，差点据此给出错误的"严重超标"结论。
> **校准判据**：算出的数字拿去和 `/context` 的 `Memory files` 对，**对得上才说明比率适用**；对不上就改用实测值。

---

## 第 2 步：分「机制」vs「配置」⭐ 本技能的核心

**这一步做错，后面全白费。**

Claude Code 有一批**由机制决定的加载行为** —— 它们不是配置问题，**改不了**，只能顺着它减文件：

| 现象 | 归因 | 能治吗 |
|------|------|:--:|
| `.claude/rules/` 下的 md **被自动加载**（即使没有任何 `@` 引用） | **机制** | ❌ 只能**减文件** |
| 技能**只常驻 `description`**（约 70 tokens/个），正文触发才读 | **机制**（渐进披露） | ❌ 已是最省表示 |
| **技能正文 / 模板 / 历史文档不占常驻** | **机制**（按需读） | ❌ **别去压它**（白费） |
| 子 Agent **只常驻 name + description** | **机制** | ❌ 已经很省 |
| **同一内容被多级 `.claude/` 各加载一遍** | **配置问题** | ✅ **可治** |
| **单文件几百行全塞一处** | **配置问题** | ✅ **可治** |
| **入口文件超 200/400 行** | **配置问题** | ✅ **可治** |

### ⚠️ 同名冲突的优先级（方向不一致，别凭直觉类推）

| 对象 | 同名时谁赢 | 出处 |
|------|-----------|------|
| **Skills** | **个人 > 项目**（`~/.claude/skills/` **压过** `<项目>/.claude/skills/`） | Claude Code 官方 skills 文档 |
| **Agents** | **项目 > 个人**（**方向相反**） | Claude Code 官方 sub-agents 文档 |
| **CLAUDE.md** | **全部拼接，不覆盖**；真冲突时模型可能任选 | Claude Code 官方 memory 文档 |

> **由此推两条**：① 要项目级说了算 → **别在个人级装同名技能**；② 两头都装 → **必须版本一致**，否则赢的那份可能是旧的。

### 判别动作

```bash
# 找出「多级 .claude/ 里内容完全相同」的重复文件
# 先列同名文件，再比 md5 —— md5 相同 = 纯浪费
```

**判据**：**「这个加载行为是 Claude Code 定的，还是我配置出来的？」**
- 机制 → 只能减文件（如把重复的那份从子级移走，父级会提供同内容）
- 配置 → 可以拆、可以指针化、可以瘦身

---

## 第 3 步：算 Multi-Agent 乘数 ⭐ 收益估算的依据

**子 Agent 每次启动都要重新加载一遍常驻层。** 所以：

```
单 agent 启动成本 ≈ CLAUDE.md+rules + 技能索引 + 系统 prompt/工具定义
                  ≈ 常驻层 + 固定开销

N 个并行 agent 的常驻开销 ≈ N × 上述
```

**怎么测**：

```bash
# 用 /context 拿到三个数：Memory files + Skills + (System prompt + System tools)
# 相加 = 常驻层。再 × N（典型并行 agent 数）= 乘数后的成本
```

**关键判断**：
- 如果**常驻层 > 窗口 5%**，且用户**常派子 Agent** → **这是最该先做的一类优化**（收益乘 N）
- 如果用户**基本单会话** → 常驻层收益有限，重点转向「会话内容」（见第 5 步的报告建议）

> ⚠️ **别把"技能正文大小"算进常驻** —— 它不常驻。曾有人去压 20 多个 40KB 的模板文件，**一个 token 都省不下来**。

---

## 第 4 步：安全诊断（与省 token 并行的一路）

体积之外，顺手查四类**安全问题**——它们常与"配置膨胀"同源（都是长期没人管的沉淀）：

| # | 查什么 | 怎么查 | 危险信号 |
|:--:|--------|--------|---------|
| 1 | **权限过宽** | 看 `settings.json` / `settings.local.json` 的 `permissions.allow` | 出现 `Bash(*)` / `Bash(rm *)` / 通配过宽的条目 |
| 2 | **凭据残留** | 扫配置与脚本里的明文密码 / token / 私钥 | 任何硬编码凭据（含"看起来无所谓"的测试凭据） |
| 3 | **hook 有效性** | 逐个确认 hook 指向的脚本**真实存在且可执行** | hook 指向已删除的脚本 → **静默失效**（比没有更危险） |
| 4 | **内容红线** | 若工作区有会外发的面（私有 npm / 公开仓），扫其中的客户名 / 项目代号 / 内部系统名 | 任何真实业务数据进入可外传面 |

> **判据**：**「这条配置/文件，如果被别人看到 / 如果它悄悄失效了，会怎样？」**

---

## 第 5 步：出报告（五分类，不动手）

**每条发现归一类**，避免"一刀切删"：

| 分类 | 含义 | 谁来定 |
|------|------|--------|
| **KEEP** | 真资产 / 红线 / 机械门禁 | — |
| **SIMPLIFY** | 有用但啰嗦，留其义、压其形 | agent |
| **MOVE** | 有价值但非"每次都要" → 沉降为按需加载 | agent |
| **DELETE** | 纯冗余 / 重复注入 / 死规则 | **人确认** |
| **CONFLICT** | 规则打架 / 语义歧义 / 声明与实际不符 | **人裁决** |

报告模板：

```markdown
## 0. 一句话结论（省多少 × 多少 agent）
## 1. 成本结构（单会话 / 单 agent / N agent）
## 2. 机制 vs 配置（哪些改不了、哪些是我们的问题）⭐
## 3. 发现清单（P0 超标 / P1 可沉降 / P2 微优化，每条五分类）
## 4. 收益测算（单会话 vs N agent 两列）
## 5. 角色分工（人管什么 / agent 管什么 / hook 管什么）
## 6. 建议执行顺序（低风险 → 需人裁 → 需设计）
## 7. 决策沉淀（每条"为什么删/为什么留"，供下次复用）
```

**优先级约定**：
- **P0** = 体积超标 / 重复注入 / 死 hook
- **P1** = 可沉降 / 语义重叠
- **P2** = 微优化（不影响常驻的，**默认不动**）

---

## 第 6 步：执行（**只做可逆操作**）

⚠️ **Phase 4 人审不可跳过**：把报告 + 五分类交人，**等确认后才动手**。

动手纪律：

| # | 纪律 |
|:--:|------|
| 1 | **备份先行** —— 改任何文件前先快照（`cp` 为 `*.bak-YYYYMMDD` 或走工作区备份脚本） |
| 2 | **只移不删** —— 用 `mv` 到回收站，不用 `rm`；确认无恙后再由人决定是否真删 |
| 3 | **单文件试点** —— 批量前先拿一个文件试跑，确认无副作用再推广 |
| 4 | **改后 diff 复核** —— 确认没有核心语义被误删 |
| 5 | **范围隔离** —— 只治当前工作区；不碰全局环境变量 / 他人配置 |

> 🔴 **绝不使用 `rm -rf`**（无论什么场景）。清理一律 `mv` 到临时区。

---

## 第 7 步：回归验证（**不能省**）

改完必须验证三样，**否则等于没治**：

| # | 验什么 | 怎么验 |
|:--:|--------|--------|
| 1 | **体积断言** | 重跑第 1 步的量，确认达标（常驻 < 5%） |
| 2 | **结构合法** | 入口文件 / 配置结构仍合法；关键旋钮未被误降级 |
| 3 | **功能冒烟** | 被治理的入口仍可调用（常用命令 / 关键技能能起） |

> **判据**：**「改完能用一个数字证明变小了吗？改完功能还正常吗？」** 答不上 = 没验证。

---

## 第 8 步：留痕（防下个会话再膨胀）

- 把「本次发现 + 处置 + 为什么」写进**变更日志**（或工作区的治理记录）
- 有跨会话记忆的工作区 → 同步一条记忆（记**根因**，不只是结论）

> **只改文件不写记录 = 下个会话照旧膨胀**，等于没治。

## 排错

| 现象 | 真原因 | 怎么办 |
|------|--------|--------|
| 压了之后**一点没省** | 压的是**不占常驻**的东西（技能正文 / 模板 / 历史文档） | 回到第 2 步，先分机制 vs 配置 |
| 删了文件后**报错 / 行为变了** | 该文件被隐式引用（脚本读它 / 别的规则指它） | 从回收站恢复；改用**指针化**（留一句"细则见 X"）代替删除 |
| 「我明明删了，怎么还在加载」 | 同名文件在**另一级** `.claude/` 下（个人级 / 项目级） | 查同名优先级表（Skills 个人>项目，**方向与 Agents 相反**） |
| 子 agent 还是贵 | 常驻层没减，或 dispatch 时把**会话背景**塞进了 prompt | ① 看第 3 步乘数 ② 派活只给**任务 + 关键文件路径**，别给会话历史 |
| 改了配置但**下一会话没生效** | 配置文件位置不对 / 需重启会话 | 确认改的是当前生效的那份；`/clear` 重载或重开会话 |
| 体积看着降了，**用户还是觉得贵** | 大头在**会话内容**（Messages），不在常驻 | 常驻优化有上限；长会话的解法是**及时沉淀 + 开新会话**，不是压配置 |
| 算出的 token 数**明显偏大**（差 2-3 倍） | 换算比率拍脑袋定的（如按"中文 1.5 字符/token"） | 用 **4.6 字符/token**；并拿 `/context` 的实测值校准 |
| 审计脚本在 macOS 报 `declare: -A: invalid option` | **macOS 自带 bash 是 3.2**，不支持关联数组（需 4.0+） | **别用 `declare -A`** —— 改用临时文件 + `grep`/`cut` 比对 |
| 重复检测报"未发现"，但明明有 | 只查了 `$PWD/.claude` 和 `~/.claude`，**漏了祖先目录** | Claude Code 加载 **cwd 及其所有祖先**的 `.claude/` —— 收集时要**沿祖先链向上遍历**，并去重 |

---

## 红线

- ❌ **不用 `rm -rf`**（任何场景）；清理一律 `mv` 到临时区
- ❌ **不跨工作区改** —— 不碰全局环境变量 / 他人配置 / 别的项目
- ❌ **不擅自做语义取舍** —— 「这条规则还要不要」归人；只做可逆操作
- ❌ **不按触发频次自动关组件** —— 低频 ≠ 无用，dormant 名单必须人拍板
- ❌ **不把"看起来没用"的文件直接删** —— 先查引用，再沉降
- ✅ **备份先行 + 改后 diff + 回归验证**（三样缺一不可）
- ✅ **报告里标清「机制」还是「配置」** —— 让人知道哪些是白费力气
