# publish-package-review

## 何时用

- 发布包定稿后、**定时发布前**，需要一轮"能不能发、哪里会翻车"的审核
- 内容已经改了多版（v1→v7），需要确认配套文档、配图、合集、摘要是否全部跟上
- AI 生成/辅助生成的内容，需要用可视化方式让人快速核对
- 触发词：审校 / 审核发布包 / 发布前检查 / 继续审查 / 对账 / 版本漂移

## 核心判断（最重要的一条）

**AI 生成内容的问题，往往不在正文里，而在正文周围的"说明书"里。**

正文改了 7 版，`发布操作单.md` / `待办总清单.md` / `配图说明.md` 还停在 v2 —— 这种**版本漂移**
才是发布当晚最容易翻车的地方。审校第一动作不是读正文，是**拿正文实际口径去对账所有配套文档**。

## 两条铁律

### 铁律 1 · 数字溯源：答不上"第一次出现在哪一行"就删

对包内出现的**每一个数字**问一句：**它在素材库里的第一次出现是哪一行？**

- 答得出来 → 记为"有源"，可在看板 D 级正面确认
- 答不出来 → 一律删除，不降级、不软化、不"大概其"

真实案例（TREND-03，2026-09-13）：包内三处写「2098 人」，素材库 25 份文档**零命中**——
首次出现即在包的输出侧（`标题摘要.md`），然后传染到操作单与审查 brief。
更糟的是操作单 v1 写"**报名**"，刷新时被写成"**到场**"，把没源的数字又推进一步。
最终处置：三处全删，宁可少一个数字，不能多一个可疑数字。

**易混陷阱**：素材库里存在的相近数字可能属于**完全不同的对象**。
（上例中"1800 人实际开放"是央企知识库自身的用户口径，与大会无关。）

### 铁律 2 · 正文散文不动，只出建议

审校**不改正文的句子**。正文级改动（措辞、限定语、代词）以 **B 级建议**列出，等作者拍板。
审校者只做三类确定性修正：**元数据**（版本号/字数）、**路径**、**名称用字统一**。

### 铁律 3 · 包必须自洽：正文引用的实体资产要在包内

凡正文引用的**实体文件**（配图 / 封面 / 附件 / 数据表）都必须**拷贝进发布包**。
写"直接引用自 `<别处路径>`，不复制到本目录"= 没做——排版时会跑去别处捞图，包不自洽。

- 配图命名：`序号_语义.webp`，**序号即上传顺序**；同时在本包说明里保留"原文件名 ⇄ 本包文件名"对照，便于回溯
- 备选图放子目录 `备选池/`
- 拷贝后**必须实图核对**（不能只看文件名）：① 用 PIL 验证可打开 + 尺寸；② 拼联络表扫一眼确认内容与论点对得上
- **检查构图方向**：竖构图在公众号里会被拉得很长。
  真实案例：第 3 张配图是唯一的 1440×1920 竖构图、观众后脑勺占大半，但内容最准（是 `load_skill` 那一页代码）。
  处置是**保留原图 + 另拷横版替代进备选池 + 说明里写清取舍**，交由作者发布前定，**不建议排版中途换图**

## 审校看板结构（四档分档）

单文件零依赖 HTML。顺序固定：

0. **结论置顶**（红框）——一句话说清"哪里会出事"，让人三分钟决定放不放行
1. 发布状态表（形态/排期/合集/定稿/封面/配图/原创闸门）
2. 包结构地图 + 资产清单
3. 门禁检查表（逐项：阈值 / 实际 / 结论）
4. 版本迭代史（时间线，每版"改了什么 + 为什么"）
5. 关键决策留痕（D1…Dn）
6. **本轮审查发现**——A 必改（阻塞发布）/ B 建议改（等人拍板）/ C 素材侧错（正文没错）/ D 已核实无误
7. 素材溯源总览
8. 配图清单（正文实用 N 张 + 备选池）
9. 待办与发布后动作
10. **看板技巧**（把这套方法论本身写进去，看板即 SOP）
11. 页脚（审校范围 + 证据文件清单）

### 分档的意义

| 档 | 含义 | 处置 |
|---|---|---|
| A | 阻塞发布，照做会出错 | 直接修，看板标注「已修」 |
| B | 涉及正文散文 | 只提建议，等拍板 |
| C | 正文是对的，素材库写错了 | 修素材库，看板注明"正文无误" |
| D | 已核实无误 | **正面确认**，发"可以放行"的通行证 |

**D 级必须列。** 只列问题会让人以为满盘皆错；审校和找茬的区别就在这里。

## 版本漂移对账清单（逐项必查）

| 检查项 | 常见漂移 |
|---|---|
| 正文文件路径 | 指向 `_archive/` 里已归档的旧版 |
| 字数 | 操作单写 3800，定稿实际 3200 |
| 配图数量 | 说明写 7 张，正文实际只有 3 个占位 |
| 合集名 | 操作单写 A，定稿/后台是 B |
| 讲者/人名用字 | 同音字混用（凯瑞/凯锐），或某份文档用了别名 |
| 机构名 | 两套写法并存（AI 特区 / Agent 特区） |
| frontmatter 元数据 | 文件名 v7，文件头 `status: v6` |
| 素材归属 | 同一句话在不同文档归给了不同讲者 |
| **术语** | 语音转写同音词污染（真实案例：`AI First` → `AI Force`，一次污染 31 处 + 4 张成品图）。改术语**不是改一处**：要连带素材源、派生资产（**信息图 HTML 改了 PNG 不会自动更新，必须重渲染 + 实图核对**）、发布包配图说明、CHANGELOG。术语 SSoT 见 `rules/TERMS.md`（若存在） |
| 外部链接 | 未做连通性复核（离线审校的天然盲区，要显式标注） |
| **"顶部有警示但表没改"** | 真实案例（MODEL-02，2026-09-14）：发布参考顶部挂了「以 v4 为准」的警示横幅，但下方**「发布参数」表格里的标题/摘要仍是 v3 下线版**——照表操作就是把旧标题发出去。**横幅 ≠ 已同步**：凡是"参数表/操作表"，必须逐格拿定稿口径比对，不能因为顶部有说明就跳过 |
| **规则库口径 vs 唯一事实源冲突** | 真实案例（MODEL-02）：规则 PUB-019 写「主文晚 20:15」，而发布日历（唯一事实源）9/11 已改为「早 8:15」——**规则文字滞后于决策 1~N 天**。凡涉「时段/口径/流程」，去对唯一事实源 + 后台实证，发现打架**先修基建再把结论说出口** |
| **草稿箱/线上版本落后于本地定稿** | 线上已有实体资产（图片已上传、编辑器侧有人工改动）时，**不要重新生成整包注入**（会冲掉图与人工改动）。正确产出是「逐块补丁」：找到这段 → 替换成这段 + 列出不用动的部分 + 标注要替换的图 |
| **实体资产** | 配图/附件只在说明里"引用"而没拷进包（见铁律 3）；或正文占位路径与包内文件名对不上 |
| **数字出处** | 见铁律 1：输出侧凭空出现的数字 |

## 长图截图（macOS 实操）

```bash
CHROME="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"
"$CHROME" --headless=new \
  --no-sandbox --disable-setuid-sandbox \        # 沙箱内必须，否则 GPU 进程 FATAL 退出
  --disable-gpu --disable-dev-shm-usage --hide-scrollbars \
  --force-device-scale-factor=1 \                # 1 = 便于分享；2 = 高清母版
  --window-size=1120,9200 \                      # 高度给足，截图后裁
  --screenshot="/tmp/raw.png" "file:///abs/path/x.html"
```

再用 `scripts/crop_tail.py` 裁掉尾部空白：

```bash
python3 scripts/crop_tail.py /tmp/raw.png out.png --bg 247,248,250 --pad 40
```

> 关键点：Chrome 的 `--screenshot` 只截 `--window-size` 的尺寸，**不会自动全页**。
> 所以高度要给足，再靠裁剪收边。`--no-sandbox` 是必需的，不加直接崩。

## 从实拍 PPT 蒸馏配色（可选步骤）

需要"借用"某套讲稿/品牌色系时，**不要目测，要采样**：

1. **不要整图量化**——照片里墙面、地毯、观众会污染主色
2. **取白参考**：在幻灯片正文区的白底部分取最亮一批像素求均值
3. **按白参考归一化**后，再挑高饱和像素（H/S/V 阈值）取众数
4. 校正前后差距是实质性的：上例橙红 `#CC5448 → #F2644F`、荧光绿 `#3CD878 → #46FA8C`

**边界**：借色系可以，**不借版式**。PPT 的上下横带、多栏语法属于 PPT 语言，搬到封面/文章会打架。

## 通篇连贯性审查（长文专用，稿件扩写后必做）

稿件一扩写（比如从 3000 字扩到 10000 字），最容易留下的是**"局部改好了、整体没跟上"**。逐段过一遍时按这 6 条查：

| # | 查什么 | 真实案例 |
|---|---|---|
| 1 | **开头的承诺 vs 全文篇幅是否匹配** | 文章从"下午六场"扩成"一整天"，开头"先说结论"的三条却还全是下午视角 → 头重脚轻，需补一条覆盖新增部分 |
| 2 | **每个时刻回素材核对**，尤其"开始/结束"这类边界时间 | 把作者**出发时间**写成了大会开始时间。这类错最隐蔽，因为素材里可能本身就记错了——查到源头后仍要以作者口径为准 |
| 3 | **人名归属三源交叉** | 一句金句：纪要写"主持人总结"、台账挂在另一人名下、时间戳又早于该讲者上场 → 三源打架，按"不猜不硬安"处理，信源表拆行 |
| 4 | **前向引用** | 前文说"中午发布的那张图…"，但"中午"要到后文才登场 → 改成事后回指（"后来中午发布的那张…"） |
| 5 | **倒叙需要锚点** | 短稿里倒叙没问题；长稿里跨度一大读者就断片 → 补一句"回到下午开场那一刻" |
| 6 | **避免整句重抄** | 前文引过的原话，后文回扣时又抄一遍 → 只做指认（"就是上午那两句"），不重抄 |

另外两条经验：
- **加粗数量是 AI 味的硬指标**。长稿初稿很容易写到 50+ 处加粗——已属 AI 生成特征，应收敛到个位数。
  注意：删加粗时若原文是"**关键词。** 正文…"这种结构，会留下"XXX。 正文"的悬空句，**要顺手改成破折号或冒号**。
- **门禁阈值要跟着篇幅重新审视**：`加粗 ≤8 / 引用块 ≤3` 是为 3000 字设的。
  扩到 1 万字若仍硬套，会逼你把引语全塞进行内引号（可以接受但读感变差）；
  建议要么按比例重设阈值并**记入门禁表**，要么明确保留原阈值并**在 README 标注例外**。

## 在场叙事溯源（体验型长文必做，与去 AI 味同轮做）

第一人称写作里，**客观事件断言必须能回素材；心态修辞属于作者权限**。这条界不清，文章就会长出"编出来的现场"。

本轮实测（TREND-03，2026-09-13，boss 点破"你再加戏么"）——扫描后共 **13 处**：

**必须删（无源）**

| 类型 | 案例 | 判据 |
|---|---|---|
| 他人反应 | 「我旁边的朋友小声说，这不就是我们公司吗」「他说了一句我旁边朋友笑了一声、我没笑出来的话」「朋友没接话」 | 素材库"朋友"**0 次**，同行者无任何记录 |
| 群体反应 | 「这句把全场逗笑了」 | 素材库"逗笑 / 笑了"**0 次** |
| 第一人称动作 | 「我当场记在了本子上」「我拍下来了」「我单独记了」 | 无素材支撑的物理动作 |
| 虚设同行 | 摘要行「我跟朋友去北京中关村参加」 | 同"朋友" = 0 |

**允许保留（作者权限内）**：椅子还没坐热 / 抱着听热闹的心态 / 我盯着这句看了半天 / 我到现在还记得。
**但要控频**：同一动词（"记"）全文出现 6 次就是套路，收敛到 3 处以内。

**高频归属错：把素材整理者的批注当讲者原话。**

案例：「内容生产成本趋零」在素材里是 OCR 表格**第三列的批注**（`PEC/13` K34），不是讲者原话；
正文却写成"他说的'内容生产成本趋零'"。→ 改回作者自己的判断，别挂在讲者名下。

**别误杀：标了【OCR】的引语是有源的。**

案例：「深入一线扎实填坑，连接业务长效修路」全库**文本** 0 命中，但 `PEC/02` 金句库第 78 行标着 **【OCR】**——
它是现场 PPT 图上实拍的，属可用素材。
**"搜不到" ≠ "不存在"**；先分清是"文本没记下来"还是"事情没发生"，前者补标注，后者才删。

**批量手段**：别目测。脚本扫三类模式再逐行判——
① `朋友|旁边|小声|邻座` ② `拍了|记在|记了|记下来` ③ `全场|掌声|哄|逗笑` + `我[^\n]{0,3}(拍|记|笑|看|听|说)`。

**替换原则**：删掉没源的戏之后若上下文出现落差，**优先用作者自己"有源的判断"补位**
（例：用 `PEC/14 A1` 的"组织层 AI Force 比个人层难得多"替换"朋友小声说"），而不是再编一句过渡——
**用真实的观点换掉虚构的场景，这样净字数几乎不涨，深度反而上去。**

## 输出规范

- 看板：`<包>/06_发布参考/<编号>_发布包审校看板_YYYY-MM-DD.html` + 同名 `.png`
- 风格：light 主题，行途技术蓝 `#056de8` 作主色，直角、细线、无阴影
- 证据必须**回挂到文件 + 原文片段**，禁止写"经分析认为可信"
- 收尾必做：`CHANGELOG` 追加审校轮记录 + `待办总清单` 刷新 + daily memory 追加

## 常见坑

- 数字幻觉跨文档传染（见铁律 1）
- **重渲染派生图时，参数复现不了就别硬覆盖**。真实案例：改了信息图 HTML 里的术语，想同步重渲 PNG，
  但原图是"窄逻辑宽 + scale-factor"生成的，标准 headless 复现不出同样布局
  （`--force-device-scale-factor` 只影响输出分辨率、**不参与 CSS 布局**；换个逻辑宽，字号与图高全变）。
  正确处置：**从 `.backups/*.tar.gz` 恢复原图**（`tarfile` 按名过滤，注意 tar 把中文路径转义成八进制），
  原图先用着，把"重渲染"记为待办 —— **别拿"看起来差不多"的参数覆盖确定的东西**。
- **第一人称"加戏"**：编出来的现场反应（他人的话、群体反应、自己拍/记的动作）比错数字更隐蔽——
  读者无法验证，但**作者本人一眼就识破**，且一旦被识破，全文真实性一起掉价（见"在场叙事溯源"）
- 把"报名数"写成"到场数"——口径升级比数字错误更严重，因为它更难被发现
- 只截图不看截图：导出后**必须自己 Read 一遍 PNG**，确认没有溢出、截断、错位
- 审校范围要写进页脚（"全包 N 个目录 M 个文件 + 素材库 K 份文档"），否则无法判断审校是否完整
