# 技能命名查证（Skill Naming Evidence）

> 第 0.5 步：先查用户怎么说这件事。
> 原则：**技能名从用户嘴里来，不从 AI 的技术词汇来。**

## 为什么

2026-10-22 实测：一个技能叫 `html-deck`，翻 52 个会话发现用户说过 4 次「ppt」、0 次「deck」。用户回头问"这个是啥"。
名字错了不是不好听，是**用户想用它时搜不到**——skill 的 description 是唯一触发机制，名字与触发词脱节 = 技能形同虚设。

## 时机与成本

| 阶段 | 改名成本 |
|---|---|
| 本地目录（未发布） | `mv` 一次 |
| 已发 npm / 全局池 | 包名**改不了**，只能发新包 + deprecate 旧的 |

**发布前跑一次，成本最低。**

## 步骤

### 第 0.5 步：查用户实际用词（必跑）

在历史会话转录目录（Claude Code / WorkBuddy / 豆包等，按工具各自命名规则）下，只取用户消息，统计他实际用的词：

```bash
# 在 ~/.claude/projects/<项目>/ 或 ~/.workbuddy/projects/<项目>/ 下（目录名按工具命名规则带或不带 - 前缀）
grep -h '"type":"user"' *.jsonl | grep -o '关键词1\|关键词2' | sort | uniq -c | sort -rn
```

> 注：WorkBuddy 会话里 `<cb_summary>`/`<conversation_history_summary>`/`<task-notification>`/`<system-reminder>` 是框架注入不是用户原话，统计前先过滤；可配合 `session-distill` 技能的消息抽取与词频脚本更省事。

### 判定表

| 查什么 | 结论 |
|---|---|
| 用户**反复说**同一个词（≥3 次） | 需求稳定 → **该建**，且用**这个词**当技能名 |
| 用户说的词 ≫ 你打算用的技术词 | **改名**，或至少把用户词写进 `description` 做触发 |
| 用户只有一次提及，但表达"每次手工做很烦" | 看**痛点强度**，不看词频 → 该建 |
| 用户从没提过，但同类动作跨项目重复 | 查**跨项目**转录再定 |

### 写进 description

- `name` 用用户词对应的 kebab-case（英文目录名惯例），**用户原话必须进 `description`**。
- `description` 覆盖三层：用户怎么叫这件事 + 等价口语触发词 + 反例边界（什么场景不用）。
- 触发词宁多勿少：用户搜的是口语，不是你的技术词。

### 留痕

- 新建/改名登记项目 `CHANGELOG` + 产出索引；若技能仓/工作区带台账生成脚本（如 `tools/skill_ledger.py`）则重生成技能台账。
- 适用范围：工作区专属技能须带范围守卫（读根 `AGENTS.md` 含空间标识才执行），其他项目不适用。
