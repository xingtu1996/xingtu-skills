# 简单即真（Simplicity / YAGNI）

> - 含义：极简 = 高效，能删则删。复杂不是聪明，是没想透
> - 核心机制：只解今天的问题，不为假想的未来抽象；简单 ≠ 简陋，简单 = 充分理解
> - 适用场景：设计方案、写代码、写规则、搭流程时做减法

## 提示词文本（直接复制使用）

```
请用「简单即真」的原则评审/设计：「（方案/代码/规则）」。

要求：
1. 能删则删：逐条检查，删掉会犯错吗？不会 → 删；
2. 已有优先：已有实现、标准库、平台能覆盖吗？先复用再新增；
3. 只解今天的问题：这是「今天需要」还是「将来可能需要」？将来需要 ≠ 现在做（YAGNI）；
4. 最短可用：一行能解决就一行，最短可工作的方案才是终点；
5. 简单 ≠ 简陋：说明你删了什么、为什么删，确保删完仍是充分理解后的完整方案。
```

## 反模式（要避免的）

- **过度工程**：为「迟早要用」建抽象/接口/配置——预测常错，真到用时需求已变
- **为未来抽象**：一个实现套接口、一个产品套工厂——抽象等有第二个时再抽
- **写多当交付**：输出量 ≠ 价值，使劲推但问题没动，就没做功

## 用法示例

- 「用简单即真的原则评审：我这个功能设计」→ 逐项删掉「将来可能用到」的部分
- 「用简单即真的原则写：一条发布检查规则」→ 每条规则问「删掉会犯错吗」，只留会犯错的
- 「用简单即真的原则设计：这个模块的接口」→ 只有单个使用者时不抽象

## 使用技巧

- 每条规则/代码/配置都问一句：「删掉会犯错吗？不会 → 删」
- 体积即成本：常驻的东西越多，每次都要带着跑（上下文/内存都是税）
- 知识只记一遍，不双写，防两处不一致
