# 决策点确认清单（Decision Points to Confirm）

> - 含义：把一份模糊的问题描述，重写成一组业务方能直接拍板的决策点，每个点都是"现状/问题/请确认"三段式
> - 核心机制：技术人容易直接给方案，但业务方需要先知道"要决定什么"；结构化决策点让对方勾选项而不是写小作文
> - 适用场景：需求评审前、跨部门对齐、把模糊问题抛给产品/业务方时

## 提示词文本（直接复制使用）

```
以下是一份技术排查/问题描述，请帮我重写成「需要业务确认的决策点」清单，抛给业务方拍板。

## 原始描述
【粘贴原始问题/排查记录】

## 要求
1. 从原始描述中提炼出 N 个决策点（D1~Dn），每个决策点格式：
   - 标题：一句话说清要决定什么（用业务语言，不是技术语言）
   - **现状**：系统现在是怎么做的
   - **问题**：现状在什么场景下出问题
   - **请确认**：需要对方拍板的具体选项（给 2-3 个可选答案，不要开放式提问）
2. 从第一性原理出发重写提问：不要假设"就是要改代码"——先问清"这是不是真问题"、"问题属于哪一层"
3. 区分：
   - 哪些是规则不一致需要统一的
   - 哪些是历史数据需要处理的
   - 哪些是是否并入已有需求的
   - 哪些是影响面需要排查的
4. 按优先级排序：影响线上业务的排前面
5. 每个决策点标注【核心】/【次要】

## 输出
D1~Dn 清单，每个严格按"现状/问题/请确认"三段式。最后加一段"如果这些都确认了，下一步是什么"。
```

## 反模式（要避免的）

- **开放式提问**："你觉得应该怎么做？"——业务方没法答；要给选项
- **技术黑话**：不说"关联哪个出库单"，说"refNo 应该取哪条分支"
- **没现状直接问**：业务方不知道现状就没法判断
- **把方案当问题**："请确认是否要加提示"——这已经是方案了，问题应该是"为什么会找不到"

## 用法示例

- 换货退货关联错出库单：D1 换货退货应固定关联哪张出库单？D2 先发新货还是先收旧货？D3 出库单还没生成时怎么办？
- AI 报表口径分歧：D1 这个指标的分母包不包含退款单？D2 历史数据要不要重刷？

## 使用技巧

- "请确认"后面一定是可勾选的选项，不是问号
- 先问"是不是真问题"再问"怎么改"——很多问题是测试数据造成的假问题
- 业务方答完后，每个决策点直接转成一条需求/一条规则
