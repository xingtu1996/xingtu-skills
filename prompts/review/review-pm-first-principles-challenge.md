# 产品经理第一性原理质疑（PM First-Principles Challenge）

> - 含义：以产品经理 + 第一性原理视角，对一份"需求提案"做对抗式质疑，先问"这是不是真需求"再问"怎么实现"
> - 核心机制：技术人接到需求就想怎么实现，但很多需求是伪问题（测试数据造成的、过度设计的、治标不治本的）
> - 适用场景：评审产品需求、看技术方案前、讨论"要不要做这个优化"

## 提示词文本（直接复制使用）

```
以资深产品经理 + 第一性原理视角，对抗审查这份需求提案，找出薄弱点。

## 审查对象
【粘贴提案/需求文档路径或内容】

## 背景
【两个实测问题/痛点是什么，产品给了什么改法】

## 请质疑（第一性原理，不客气）
1. **两个问题是否真需求？** 还是测试数据/脏数据/老数据造成的伪问题？时间窗/边界问题在真实业务（新数据）下还会发生吗？
2. **提案是不是治标不治本？** 根因若是【某个多余的限制/某行错误代码】，那正解是不是直接改那行，而非加一堆提示/引导？
3. **防呆提示 vs 直接放开**：如果直接放开限制（改 N 行），还需要提示吗？提示方案是不是过度设计？
4. **全量展示/放开的风险**：放出不可选选项，会不会带来新困惑/更多客诉？大流量下体验如何？
5. **优先级/价值**：这两个提案 vs 其他已知待办，值不值得现在做？
6. **被忽略的角色/场景**：运营配置者视角、非技术用户、历史数据订单、异常订单，都覆盖了吗？

## 输出
结构化质疑清单：每条 = 质疑点 + 依据 + 反方结论/建议。
标严重度：🔴 阻塞（需求本身有问题）/ 🟡 需关注 / 🟢 可接受。
禁客套。
```

## 反模式（要避免的）

- **直接接受需求进入设计**：跳过"是不是真需求"这一问
- **认同所有提示类方案**：弹窗提示、置灰引导、防呆文案是产品经理的舒适区，恰恰最容易过度设计
- **不考虑脏数据**：测试订单是 2020 年的，真实新订单根本不踩这个坑
- **忽略被忽略的角色**：只看主力用户，不看运营/客服/历史数据

## 用法示例

- 提案"给弹窗加活动有效期提示"：质疑——订单时间在活动外，是因为测试数据老，真实新订单不会发生
- 提案"把下拉改成全量展示"：质疑——直接放开 1:1 限制只改一行，全量展示反而引入新问题

## 使用技巧

- 第一问永远是"这是不是真问题"——80% 的需求死在这一问
- 区分"加提示"和"修根因"：能改一行代码解决的，不要用交互设计解决
- 质疑完给"反方结论/建议"，不要只拆不建
