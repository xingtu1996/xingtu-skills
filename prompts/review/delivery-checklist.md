# 交付检视（Delivery Checklist）

> - 含义：宣称「代码完成」前的最后一道闸，防「假完成」
> - 核心机制：代码写完 ≠ 功能完整；六维检查 + 全链路差距分析
> - 适用场景：提交前、宣称完成前、评审前

## 提示词文本（直接复制使用）

```
代码写完 ≠ 功能完整。请按「交付检视」检查：「（声称完成的改动）」。

1. 代码：所有入口都覆盖了吗？新建的有没有重复？
2. 数据：脚本入库了吗？新旧数据兼容吗？
3. 入口链路：所有调用路径都通吗（前端→接口→逻辑→出口）？
4. 配置：本地/测试/生产环境差异检查了吗？
5. 测试：编译零错误？接口全链路验证？已有功能回归了吗？
6. 差距分析：沿「入口→逻辑→出口→下游消费→数据脚本」走一遍，找断链。

最后回答：哪一项还没验证？凭什么说完成？
```

## 用法示例

- 「按交付检视检查：这个功能开发完了」→ 逐维检查，重点找「只测了自己这段」的假完成
- 「按交付检视检查：这次重构」→ 全链路回归 + 下游消费者确认

## 使用技巧

- 最典型的假完成：只测自己链路，出口/下游消费/数据脚本没查
- 「哪一项还没验证」是必答题，答不上来就别说完成
