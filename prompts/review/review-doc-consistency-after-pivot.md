# 重大结论修正后扫文档残留（Doc Consistency After Pivot）

> - 含义：架构/结论被实测推翻后，扫一遍所有相关文档，把残留的旧结论、互相矛盾、未核实遗漏全部揪出来
> - 核心机制：文档是 append 的，结论改了不会自动改文档；不主动扫，下次有人读旧文档就会基于错结论干活
> - 适用场景：架构方向调整、技术选型变更、重大 bug 定性反转后

## 提示词文本（直接复制使用）

```
检查 spec/文档目录【路径】的文档一致性，重点找残留的旧结论和未核查到的遗漏。

## 背景
【日期】发生重大架构/结论修正：
- 旧结论：【被推翻的说法】
- 新结论：【实测证明的新说法】
- 影响：【哪些文件/代码/配置因此改了】

## 检查任务
1. 通读所有 .md 文件：
   - 哪些文档还残留"旧结论"？列出精确文件:行号
   - 各文档对【同一对象】的描述是否互相矛盾（A 文档说 X，B 文档说 Y）？
   - 关键清单（如 N 个接口/N 个服务）的数量、分类在各文档是否一致？
2. 找未核查到的遗漏：
   - 清单里哪些项还没核实代码是否在用？
   - 哪些"标签/分类"还没在一手资料核实？
   - deliverables/ 里是否有过期数据？
3. 输出结构化报告：
   - 每个问题：文件:行号 + 现状描述 + 应改为什么
   - 按严重度排序：
     🔴 与新结论矛盾
     🟡 文档间互相不一致
     🟢 建议补充
   - 精简输出

## 约束
只读检查，不修改任何文件。
```

## 反模式（要避免的）

- **改了代码不改文档**：代码是新的，文档还是旧的，新人读文档入坑
- **只改一个文件**：同一结论在 5 个文件里写过，只改 1 个
- **不标"已废弃"**：直接删不如加一行"此结论已被 XX 推翻"，保留历史可追溯
- **不扫遗漏**：只找矛盾，不找"还没核实的"，下次还会踩

## 用法示例

- 实测证明"写 API 不需要内网调用"：扫一遍所有还写"必须内网调用"的文档
- 架构从 A 方案改成 B 方案：找所有还引用 A 方案的地方
- 一个接口被标记为"死代码"：找所有还在 PRD/测试用例里提到它的地方

## 使用技巧

- 用 grep 搜旧结论的关键词，比逐文件读快
- 矛盾点往往在"清单类"文档（对账表/映射表）和"叙述类"文档（设计文档）之间
- 报告按 🔴🟡🟢 分级，🔴 必修，🟡 排期，🟢 备忘
