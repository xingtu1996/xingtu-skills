# 验证完就停，不擅自扩范围（Verify and Stop）

> - 含义：让 AI 只做「验证/验收」这件事，达到验收条件就停手，不顺手搞清理、加测试、做优化
> - 核心机制：验收和改产品是两回事；一旦让 AI 在验证任务里「顺便修一下」，范围就失控、风险也跟着进来
> - 适用场景：交付前核验、只查不改的检查、跑测试确认状态、最后一公里验收、不想 AI 越改越多

## 提示词文本（直接复制使用）

```
这是一个「只验证、不改代码」的任务：【把验收条件/要验证的东西写在这】。

请遵守：
1. 把验收条件翻译成「最小充分证据集」——用最少的检查证明它过没过，不要铺开跑全套无关的东西；
2. 优先复用仍然有效的旧结果（只要仓库状态没变）；
3. 结论必须精确分四类：通过 / 不通过 / 无法验证（缺信息）/ 被阻塞（为什么），不要含糊；
4. 除非我明确说「顺手修」，否则不要改产品代码，不要加清理、重构、额外测试；
5. 证据足够判定后立刻停。只汇报：跑了什么命令、结果是什么、还有什么没解决的风险。
```

## 反模式（要避免的）

- **验证变重构**：让 AI 查个 bug，它「顺便」把周边代码重写了一遍
- **结论含糊**：只说「看起来没问题」，没给命令和结果，复查的人没法信
- **为了跑全量而跑全量**：验收只要 3 条证据，它跑了整套测试套件，时间和 token 全浪费
- **改了不报**：验证任务里偷偷动了代码，没人 review 就混进主分支

## 用法示例

- 「只验证：这次改动有没有把导出功能弄坏，跑一下相关用例就停，别改代码」
- 「验收条件是这三条，帮我确认过没过，缺什么证据告诉我」→ 精确分通过/不通过/无法验证
- 上线前让 AI 跑一遍验收门禁，要求「过了就停，别顺手优化」

## 使用技巧

- 「只验证不改」要在提示词里写明，否则 AI 倾向于把发现的问题一起修掉
- 让它把「通过/不通过/无法验证/被阻塞」分清楚，比一句「验证通过」有用得多
- 和「小改动别整文件重写」搭配，专治 AI 越帮越忙
- 与 code/investigate-first 的区别：那篇是**改代码前**先收集证据、有可信机制解释全部证据前不动手（先诊断后治疗）；本篇是**验证/验收任务里**别顺手改代码、证据够了就停（控范围+控停止时机）。一个防乱改，一个防验证变重构。
