# 前后端契约四类错位（Contract 4-Class Check）

> - 含义：前后端联调前，按四类经典错位逐项核对（命名风格 / 路径分类 / 字段类型 / 返回结构），提前抓出返工点
> - 核心机制：前后端返工 80% 集中在这四类——不是业务逻辑错，是契约没对齐；早发现成本低
> - 适用场景：接口设计评审、联调前自查、跨团队对接

## 提示词文本（直接复制使用）

```
你是资深 SDD（Spec-Driven Design）专家，对抗式分析一份接口设计文档，重点抓四类契约错位。

## 四类错位清单
### 1. 命名风格错位
- 后端 @RequestParam 用 camelCase，前端 api 层统一转 snake_case？
- 后端返回 camelCase，前端期待 snake_case（或反之）？
- 文档里写清了"全链路统一哪种风格"吗？

### 2. 路径分类错位
- 管理功能接口（给前端调）应该放 /admin，不是 /integration
- 集成接口（服务间 Feign 调）放 /integration
- 现有路径有没有放错类别？

### 3. 字段类型错位
- 同一个业务字段（如店铺编码），后端 A 服务是 Integer、B 服务是 String？
- Long 类型 ID 前端 JS Number 精度丢失（>2^53）？
- 文档里写清每个字段的精确类型？

### 4. 返回结构错位
- 后端返回嵌套对象，前端期待平铺？
- 空值返回 null vs 空字符串 vs 空数组？
- 分页字段名统一（pageNo/page/size/offset？）

## 任务
1. 读现有设计文档
2. 对照四类错位清单逐项检查
3. 接口设计文档应该独立成文（不和功能/数据库设计混一个文件），包含：
   - 每个接口：路径 / 方法 / 调用方（admin vs integration）
   - 每个字段：精确名 / 精确类型 / 精确是否必填
   - 命名风格约定（snake 还是 camel，全链路统一）
   - 错误码 / 空值约定

## 输出
错位清单：每条 = 错位类型 + 位置 + 现状 + 应改成什么。
```

## 反模式（要避免的）

- **接口设计和功能设计写一个文档**：混在一起，没人单独盯契约
- **文档里只写"返回店铺信息"**：不写字段名和类型，前后端各猜各的
- **改了接口不改文档**：文档和代码漂移，下次对接又踩
- **不区分 admin 和 integration**：前端和服务间调用混在一起，权限和鉴权全乱

## 用法示例

- 后端收不到前端参数：grep 发现后端要 shopCode，前端发 shop_code
- 前端拿到 ID 精度丢失：Long 没序列化成字符串
- 管理功能被错误鉴权成集成接口：放错路径

## 使用技巧

- 设计文档独立成"接口设计.md"，不和"功能设计.md""数据库设计.md"混
- 字段表格化：每行一个字段，列：精确名 / 类型 / 必填 / 含义 / 示例
- 命名风格在文档开头一句话定死，不要每个接口各写各的
