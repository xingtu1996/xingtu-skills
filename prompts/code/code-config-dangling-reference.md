# 配置引用缺失项排查（Config Dangling Reference）

> - 含义：工具/脚本/hook 配置引用了一个已经不存在的文件，每次调用都刷报错——按"误删 vs 故意下线"二分法排查
> - 核心机制：报错刷屏不阻塞但恶心；根因就两种——文件被误删该恢复，或文件故意下线但配置没清该删引用
> - 适用场景：hook 报错、CI 配置引用缺失、脚本路径变了、升级后工具找不到

## 提示词文本（直接复制使用）

```
你是配置排查员。问题现象：每次【工具】调用都提示
`【报错信息：路径 No such file or directory】`
（非阻塞 error，但刷屏）。

## 排查步骤
1. **找配置**：读项目级 + 全局配置文件，列出【工具】引用的所有脚本/文件路径
2. **对照实际文件**：ls 实际目录，找出"配置引用但文件不存在"的清单
3. **二分处置**（对每个缺失项）：
   - 查 git 历史：`git log --oneline -- <路径>` + `git show <commit>:<路径>` 看内容
     - 若是**误删/版本问题** → `git checkout` 恢复（别自己重写）
     - 若是**故意下线但配置没清** → 移除配置中对应引用（或改为已存在的替代）
4. **机制自查**：确认这个文件到底该不该存在（参考 README/CHANGELOG 说明各组件职责）
5. **修复验证**：修完后写一段循环检查——
   `for f in <引用列表>; do [ -f "$f" ] || echo "MISSING: $f"; done`
   确保零缺失
6. 若新增/恢复了脚本，重跑体积/大小门禁

## 铁律
- 禁止 rm -rf / 删除非空目录
- 改配置前先备份（cp 到 /tmp 或确认 git 可回滚）
- 只处理缺失引用问题，不顺手改其他东西

## 返回
结论（根因一句话）｜配置引用清单｜缺失项处置（恢复 or 删引用）｜验证结果。
```

## 反模式（要避免的）

- **看到报错就自己重写一个脚本**：覆盖了原有逻辑，版本漂移
- **只删引用不查历史**：把本该恢复的脚本也删了
- **不验证**：改完没跑检查，下次还报错
- **顺手大改**：排查一个缺失，把配置整个重写一遍

## 用法示例

- 每次跑命令都报 `PreToolUse hook error: xxx.sh No such file`：查 settings.json，发现 hook 引用了已删的脚本
- CI 配置引用了一个旧版本脚本路径：git log 确认是改名了，改配置指向新路径

## 使用技巧

- 先 git log 再动手——90% 的"缺失"在历史里能找到答案
- 恢复用 `git checkout <commit> -- <path>`，不要手敲
- 修完一定跑一遍"引用清单全存在"的检查循环，别靠感觉
