# 先查后改（Investigate First）

> - 含义：先收集证据再动手，有一个可信机制解释全部证据之前不修改代码
> - 核心机制：症状≠推断；假设按证据排序，先验证最可能被证伪的
> - 适用场景：未知原因的问题、偶发故障、性能退化、任何「先别急着改」的场景

## 提示词文本（直接复制使用）

```
请按「先查后改」原则处理：「（问题/故障/异常）」。

要求：
1. 分离症状和推断：观察到的事实写一行，猜测的原因单独标「推断」；
2. 追踪证据链：输入、状态变化、边界、失败输出，逐环节查；
3. 假设按证据排序：每个假设标支持它的证据，先验证最可能被证伪的；
4. 有一个可信机制解释全部证据之前，不修改任何代码；
5. 证据足够时停下，报告：原因 + 证据。未获授权不做修改。
```

## 用法示例

- 「按先查后改原则处理：接口偶尔超时」→ 分离症状和推断，追踪输入/状态/日志，有证据再定位
- 「按先查后改原则处理：这个功能时好时坏」→ 先列假设并排序，不急着改代码

## 使用技巧

- 症状和推断分开写，是最便宜的自欺防护
- 「先验证最可能被证伪的假设」——一次实验排除最多可能
- 没想清楚之前就动手改，是最贵的排查方式
