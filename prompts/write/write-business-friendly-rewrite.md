# 技术用例改业务傻瓜式（Business-Friendly Rewrite）

> - 含义：把"接口/curl/字段名"的技术描述用例，改写成"点哪/输什么/看到什么"的业务傻瓜式步骤，让不懂技术的人也能照做
> - 核心机制：同一份用例要服务两类读者——AI 执行要技术字段，业务/测试要界面操作；保留 AI 字段不动，另产一份业务可读副本
> - 适用场景：给业务方/UAT 测试用例、写用户手册、非技术同事验收

## 提示词文本（直接复制使用）

```
把以下测试用例改写为【业务傻瓜式】版本——任何能看懂文字、会用系统的人就能照做，并重新生成 CSV 副本。

## 标准（业务用例风格）
- 前置：用户有 XX 权限 / 已登录 / 已存在 XX 数据
- 步骤：界面操作路径（点击哪个菜单 → 点哪个按钮 → 输入什么 → 看到什么）——不是调用接口
- 预期：界面上看到的结果（页面跳转 / 提示文案 / 列表显示）
- 保留业务含义，但描述是"人怎么操作"

## 输入
- 用例：【JSON/CSV 文件路径】（当前是技术描述：接口/字段/断言）
- 前端页面信息：【功能对应哪个菜单/按钮】（可从路由或功能名推断）

## 任务
1. 逐条读用例，把 precondition / steps / expected 改写为业务傻瓜式界面操作
2. **保留技术字段不动**（interface / assert_http / assert_body 等 AI 执行用，本地保留）
3. 重新生成副本 CSV（列：用例编号 / 测试模块 / 用例标题 / 前置条件 / 测试步骤 / 预期结果 / 优先级 / 状态）

## 输出
- 改写数：N 条
- 样例：3 条改写前后对比（步骤：接口式 → 界面式）
- 副本 CSV：已生成
- 阻塞点：无 / 有
```

## 反模式（要避免的）

- **技术用例直接甩给业务**：业务看不懂 curl，也不会执行
- **改写时把技术字段也改了**：AI 执行用的断言字段必须保留，只改人读的部分
- **步骤写得太抽象**："进入管理页"不如"点击左侧菜单 商品中心 → 商品管理"
- **预期写技术结果**："返回 code=0"不如"页面弹出 操作成功 提示"

## 用法示例

- 21 条 AI 技术用例（含 GOODS_CATEGORY 枚举）→ 业务版（点击 商品中心/商品与物料关系/条件群组管理）
- 接口断言"assert_body.code=0" → 业务预期"提交成功，列表出现新记录"

## 使用技巧

- 保留两份：技术版给 AI 跑，业务版给人看
- 步骤一定要落到"点击 X 菜单 / 点 Y 按钮 / 输入 Z"
- 预期一定要落到"界面上看到什么"，不要落到"数据库里查到什么"
