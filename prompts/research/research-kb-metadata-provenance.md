# 知识库可信度三件套（KB Metadata Provenance）

> - 含义：每条领域知识文件头加"来源 / 可信度 / 日期"三件套，让读它的人（AI 或新人）不会把推断当事实
> - 核心机制：AI 最容易把"文档里写的"当成"实测确认的"；显式标注可信度，读的人才知道哪些能直接引用、哪些还要再验证
> - 适用场景：建项目知识库、沉淀外部平台 knowhow、整理 API 文档、写团队 wiki

## 提示词文本（直接复制使用）

```
你是领域知识库规范化实施员。按以下规范整理知识库：

## metadata 三件套（每个知识文件头必须有）
```
来源：【官方文档 URL / 代码路径 / 调研日期】
可信度：✅ 实测确认 / 🔶 文档推断待核实 / ⏳ 待联调验证
日期：YYYY-MM-DD
```

## 规则
1. **区分事实和推断**：
   - ✅ 实测确认：本地调过、日志看过、代码跑过
   - 🔶 文档推断：官方文档写的，但没实际调通过
   - ⏳ 待联调：代码写了但没环境验证
2. **不要把推断写成事实**：宁可标 🔶，也不要含糊带过
3. **按领域分目录**：业务概念 / 接口链路 / 踩坑 / 测试方法
4. **反哺机制**：每次相关工作收尾，把"新验证的结论 / 新踩的坑 / 新错误码"追加到对应文件，而不是留在会话里
5. **索引总表**：knowledge-map 登记每个 KB 容器的定位、消费者、生命周期

## 输出
- 规范化后的文件清单
- metadata 补全情况（哪些 ✅/🔶/⏳）
- 反哺机制说明
```

## 反模式（要避免的）

- **知识文件没有可信度标注**：读的人分不清哪些是金哪些是坑
- **日期缺失**：半年前的"文档推断"可能已经被官方更新推翻
- **只建目录不反哺**：知识库建好就死了，每次新踩的坑不回流
- **索引缺失**：AI 不知道有这个 KB，等于没建

## 用法示例

- 对接某开放平台后建 KB：每个接口标 ✅（本地调通）/🔶（文档写了没测）
- 沉淀踩坑：`oaid 分隔符是 |` 标 ✅ + 实测日期 + 代码行号

## 使用技巧

- 三件套越短越好，别搞成 frontmatter 模板工程
- 🔶 的条目过一段时间要重新验证，升级成 ✅ 或推翻
- 反哺比新建更重要——建一个 KB 只是起点，每次相关工作收尾追加一条才是飞轮
