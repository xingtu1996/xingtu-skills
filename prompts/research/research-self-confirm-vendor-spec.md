# 不等外部，自己查一手（Self-Confirm Vendor Spec）

> - 含义：凡是"待外部团队/渠道/供应商确认"的问题，不要干等——自己从官方文档、SDK、现有代码三条线把口径确认出来
> - 核心机制：外部响应慢、口径也未必准；一手资料（官方文档 + 实际调用 + 现有代码消费方）拼起来比等回复更快更准
> - 适用场景：对接第三方 API、跨团队接口、升级迁移时"字段映射/行为差异"类问题

## 提示词文本（直接复制使用）

```
你是【领域】口径自确认员。把以下"待外部确认"项，自己从官方文档 + SDK + 既有代码确认口径，不干等外部。

## 待确认项（每个需给出明确结论）
1. **【项 1】**：
   - 官方文档：【URL 或检索关键词】——读返回结构、字段、标注
   - SDK 类：【类名/方法】——javap/反编译看方法签名
   - 既有代码：grep 【关键词】——现有 1.0/旧版本调用方实际消费了哪些字段
   - **结论**：新接口是否同时覆盖旧语义？字段映射关系？能否用一个新分支 + 转换器同时服务？
2. **【项 2】**：同上结构

## 方法
- 官方文档：能 WebFetch 就读，不能就读 SDK 注释/反编译推断
- SDK：javap 看方法签名与 DTO 字段
- 既有代码：grep 调用点，确认实际消费字段（不是文档写什么就是什么）
- 错误码/约束：读文档说明 + 实际调用返回

## 输出
结论表：每项 = 可直接编码 / 需派生 / 真无独立接口 / 待联调。
每条结论附证据来源（文档 URL / SDK 类 / 代码行号）。
标注可信度：✅ 实测确认 / 🔶 文档推断 / ⏳ 待联调验证。
```

## 反模式（要避免的）

- **干等外部回复**：外部排期以周计，自己查一下午就能搞定
- **只信文档不看代码**：文档写的字段，现有代码可能根本没用
- **只信代码不看文档**：现有代码是旧版本，新接口语义可能变了
- **把推断当事实**：没实测的结论标 🔶，别标 ✅

## 用法示例

- 对接某开放平台 API 升级：老接口 A 和 B，新平台合并成一个接口 C——自己查 C 的返回结构 + 现有 A/B 消费字段，判断能否一个转换器同时服务
- 跨团队接口字段类型不一致：自己 grep 两边代码，找出真实使用的字段，不要等对方来对齐

## 使用技巧

- 三条线互相印证：文档说有、SDK 有、代码真在用，三者齐全才算 ✅
- 证据要落到行号/URL，不落到"我觉得"
- 结论分四类：可编码 / 需派生 / 真无 / 待联调，别含糊
